# 给 GPT 的 SYNC 任务：SocketCAN 后端 + SYNC 生产者（2026-10-16）

## 任务目标

让设备端**能在 can-2 上周期发 SYNC 帧**，为 PMP4010 的周期 PDO 路径铺路。

**本任务只做"能发 SYNC"，不做任何运动、不写任何电机参数。**

---

## 一、背景：为什么现在要做这个

厂家 2026-10-16 答复：「**现需要把 PDO 设定为同步模式，再发送同步报文**」。

主会话当天做了板端只读探测，核实了现状（证据见下）。关键结论：

- 本机 PDO 传输类型**全部是 0xFF（异步）**，所以要让它同步，**必须显式写传输类型**（`1400h:02h` 等从 0xFF 改成 0~240）——**但这是写操作，本任务不做**。
- `1006h`（通信周期）**对象不存在**（SDO 中止 `0x06020000`）→ **同步周期无法由从站配置，只能由主站定时器保证**。
- 因此：**SYNC 生产者必须由 km3 设备端自己实现**。这就是本任务。

## 三、已核实的事实（**直接采用，不要重新推导**）

全部来自 2026-10-16 板端只读探测：**零写请求**（70 个 SDO 上传请求，非读帧 0），
**两种独立实现互证**（板上标准层 `SdoClient` 与手写 CiA 301 构帧器），每种连读 5 次稳定。

### 3.1 总线与设备

| 项 | 值 |
| --- | --- |
| 逻辑 `can-2` → 内核 `can1` | 1 Mbps，`ERROR-ACTIVE`，错误计数全 0 |
| 节点 | 1（现场只接了 1 台 PMP4010） |
| 设备型号 | `PMPP4010B-CANopen-0HEB-004`，固件 `V3.3` |

### 3.2 PDO 现状

| 对象 | 实测值 |
| --- | --- |
| `1400h~1403h:02h`（RPDO1~4 传输类型） | **全部 0xFF**（异步/事件触发） |
| `1800h~1803h:02h`（TPDO1~4 传输类型） | **全部 0xFF** |
| `1800h~1803h:03h`（禁止时间） | 全部 0 |
| `1800h~1803h:05h`（事件计时器） | 全部 0 |
| RPDO1 COB-ID | `0x201`（映射：控制字 `0x60400010` + 模式 `0x60600008`） |
| **RPDO2 COB-ID** | **`0x301`（映射：目标位置 `0x607A0020` + 插补数据 `0x60C10120`）** |
| RPDO3 COB-ID | `0x401`（`0x60420010` + `0x60FF0020`） |
| RPDO4 COB-ID | `0x501`（仅 `0x60710010` 目标转矩） |
| TPDO1~4 COB-ID | `0x181` / `0x281` / `0x381` / `0x481` |

**映射与 COB-ID 与手册默认逐条相符——出厂未被改动。**

### 3.3 SYNC 相关（手册没有，实测有）

| 对象 | 实测 | 含义 |
| --- | --- | --- |
| `1005h` SYNC COB-ID | `0x80` | **存在**。设备可作 SYNC 消费者 |
| `1006h` 通信周期 | **中止 `0x06020000`** | **对象不存在** |
| `1007h` 同步窗口长度 | `0` | 存在，0 = 关闭 |

### 3.4 断线检测现状（**当前为零**）

| 对象 | 值 |
| --- | --- |
| `1017h` 生产者心跳时间 | **0（未启用）** |
| `200Ch:1Bh` 通信看门狗 | **0（未启用）** |

**总线被动监听 2 秒：收到 0 帧**（无 SYNC、无 PDO、无心跳）。
→ **当前这台电机没有任何断线检测机制生效。** 主站不发帧，它不会报异常。

### 3.5 其它实测值（写进本任务的注记，不要拿去改）

| 对象 | 实测 | 备注 |
| --- | --- | --- |
| `60C2h` 插补时间 | `20 × 10⁻¹` = **2.0 s** | **CSP 下必须与 SYNC 周期一致**，2.0s 与 4ms 差 3 个数量级——**将来要改，本任务不做** |
| `6065h` 跟随误差阈值 | 50 | 单位待核 |
| `6066h` 跟随误差时间窗 | 30000 | 若 ms 则 30 s，单位待核 |
| `607D:01h` 软限位最小 | **−2147483628** | 厂家确认此值**正确**；手册的 ±65535 是跨型号通用值，不适用 |
| `607D:02h` 软限位最大 | **2147483627** | 同上 |

### 3.6 带宽预算（取自 `实测基线.md §十`，**直接采用**）

- can-2 设计挂 **8 个节点**（PMP4010×4 + YZ-AIM×4）
- 8 节点位置环最小周期 **8 ms**（41% 占用）
- 4 节点：2 ms = **82%（临界）** / 4 ms = **41%（✓）**
- **SYNC 帧 47 µs 已在预算表内**（每周期恰好 1 帧），**不是新增负载**

### 3.7 用户已决策（不要再问）

- **位速率：1 Mbps**（`can-1` 保持 500k 不变）
- **SYNC 周期：4 ms 起步**（分层：4 台抬降走周期位置环，毛刷/刮条按事件触发）

## 四、要做的三件事（按依赖排序，一件一件来）

### 任务 1：SocketCAN 后端

`device/src/hal/` 下**目前只有 `mock_devices.cpp`**，没有真实后端。
`ICanDevice` 接口在 `device/include/km3/hal/can_device.hpp`，你必须完整实现它：

- `Backend()` → `CanBackend::SocketCan`
- `Capabilities()` → 主板 CAN：`supports_fd = false`、`max_bitrate = 1000000`
- `Send(const CanFrame&)` / `Receive(int timeout_ms)`（超时返回 `ECommandTimeout`，**不是错误**）
- `SetFilters()` / `Stats()`（含 `bus_off_count` 等——文档要求保留错误计数）
- `RecoverFromBusOff()`

**硬要求**：

1. **`Send` 遇到 FD 帧必须拒绝**，不能静默降级。参考 `canbus.py` 的报错措辞（Python 侧已有同款守卫）。
2. **`IsDlcValid()` 校验必须基于原始 `dlc`**，不得用钳制后的值——头文件注释已写明这个坑：
   早期实现用钳制值校验，导致 `dlc=9` 的经典帧一路通过。
3. **不得跨型号引用**：这个后端是通用的，不许出现 `pmp4010` 之类字样。
4. **物理标识只从配置来**：接口名从 `BusEndpoint::device` 取。
   **注意字段名的不一致是既有的、故意的**：JSON 里 CAN 端点写 `"iface"`、串口端点写
   `"device"`，**两者在 `ParseEndpoints` 里统一落到 `BusEndpoint::device`**
   （见 `device/src/common/config.cpp:69` 的注释与 `:81` 的实现）。
   **代码里不得硬编码 `can1`**。（`device/config/device.json` 的 `bus.can[]` 是唯一来源。）

### 任务 2：SYNC 生产者

实现"按固定周期在 can-2 上发一帧 COB-ID `0x080`、DLC=0、无数据、无应答"的能力。

**必须先回答并说明理由的一个设计问题（这是本任务的核心判断）**：

> **SYNC 帧由哪个线程发？**

两条路各有代价，你必须选一条并在代码注释里写清理由：

- **路 A：RT 线程周期性发**。与 1 ms 控制环同源，抖动最小。但 `write()` 是系统调用，
  **队列满时可能阻塞** —— 而 `CLAUDE.md` 硬性规则 4 与《开发规范》§1.4 明确禁止
  实时线程内做可能阻塞的操作。若选此路，必须给出"凭什么它不会阻塞"的可核查论证
  （如非阻塞套接字 + 队列满时的显式处理），**不能只写"实测没阻塞过"**。
- **路 B：边界（非实时）线程独立定时发**。与"实时环 1 ms + 总线周期解耦"的既有设计一致，
  不违反 RT 纪律。代价是抖动大一些 —— 需说明该抖动对 CANopen SYNC 是否可接受。

**不论选哪条**：

1. **周期必须来自配置**，不得硬编码 4 ms。（见任务 3）
2. **必须预先构造好帧**（`CanFrame` 是平凡类型），运行期不做任何分配。
3. **发帧失败不得静默**：要有计数与可观测出口，但**不得在 RT 路径里格式化日志**。
4. 明确 SYNC 的**起止条件**：什么时候开始发、什么时候停。
   （提示：`1007h` = 0 意味着同步窗口关闭，**SYNC 停发不会自动产生 EMCY**——
   这一条要写进注释，它是真实的现场陷阱。）

### 任务 3：配置载体

`RtParams`（`device/include/km3/config.hpp:23`）现在**没有放 SYNC 周期的字段**；
`BusEndpoint` 只有 `logical` / `device` / `baudrate` / `protocol`。

**要做的**：

1. 决定周期放哪里并说明理由。**推荐加进 `RtParams`**：`ConfigSnapshot<RtParams>`
   是给实时线程只读的，若 SYNC 由 RT 线程发（路 A），周期必须 RT 可见；
   即便走路 B，放在 RT 参数里也能让将来的周期路径同源。
2. **默认值必须是 4 ms**（用户决策），且**必须可配**。
3. 同步更新：`device/config/device.json`（现场模板）、`device/config/` 下的校验逻辑、
   以及 `ValidateConfig` 里的约束（如"周期必须 > 0 且不超过某上限"，上限自己论证）。
4. **`device/config/canopen_nodes.json` 的 `bitrate` 已是 1000000**（今天刚更正），
   不要再改它；**位速率权威来源是 `device.json` 的 `bus.can[]`**。

**注意**：`config.cpp` 有配置加载期的静默失效史（见 git log `ef3a36a`）。
新增字段必须让"配置写了但不生效"不可能发生。
