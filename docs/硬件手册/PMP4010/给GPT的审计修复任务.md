## 二、四处要修的（按依赖排序）

### 修复 1：参数写入不看使能状态

**位置**：`device/drivers/pmp4010/tools/pmp4010_params.py` 的 `execute()`

**现状**（已核实）：该文件对 `6040/6041/6060/6061` 的引用数为 **0**——
`execute()` 只对**目标对象**做 pre-read，完全不看电机是否处于使能状态。

**为什么重要**：手册把三种情况列为「不能执行命令的故障」，第一种就是
「**伺服电机在使能状态下操作保存字指令**（`1010h:01h` 写 `0x65766173`）」，
在使能状态下发保存命令会让驱动器报故障。

**⚠ 引用出处（主会话已核实并更正）**：`参数写入工具.md:40` 把出处写成
「E06 §7.7.1/故障表」。**§7.7.1 是「参数保存」，那条故障实际在 §9.4「故障检测说明」**
（提取文本第 3931 行）。两者同属保存主题但**不是同一节**——
严格说是**出处不精确**，不是瞎引。修的时候一并更正为 §9.4 / 第 3931 行。

**修法**：
1. `apply` 与 `save` 之前，**被动读一次 `6041h`（状态字）**；
2. **bit2（Operation enabled）置位则拒绝**，并明确提示"电机处于使能状态，请先失能"；
3. 读 `6041` **失败**（超时/中止）时也要**拒绝**——不能因为读不到就假定它没使能；
4. 补测试：使能态被拒、失能态放行、读取失败被拒。

**注意**：这是**新增一次只读**，不改变任何写入语义。不要顺手去改控制字或发 NMT。

### 修复 2：批次中途失败不回滚

**位置**：同上，`execute()` 的逐项循环

**现状**（已核实）：循环里某项失败就 `raise`，**前面已经写成功的项留在设备上**。
审计实测复现：transmission 批次第三项失败 → `1400:02`/`1401:02` 已是 `00`（同步），其余仍是 `ff`。

**已经做对的部分**（不要改）：
- 工具**有明确通知**——打印失败对象、期望值、读回值，并返回 rc=2。
- `1010h` save 是**独立人工动作**，所以混合态只在 RAM、**不持久**。
- `_test_params.py:146-159` 证明回滚路径本身可用。

**真实缺口**：`_test_params.py` 只断言了「只发了 1 次写且目标是批次第一项」，
**"部分成功后中止"这一情形没有测试**。

**修法**（任选其一，但要说清理由）：
- **方案 A（推荐）**：失败时**自动回滚**已成功的项到各自的 pre-read 值，
  回滚本身也回读确认；回滚失败则明确报「设备处于混合状态，需人工 `--params rollback`」。
- **方案 B**：不回滚，但**点名列出已提交的对象与它们的当前值**，
  并在输出里直接给出下一步命令（`--params rollback --backup <file>`）。

无论选哪个，**都要补"部分成功"的测试**。

**⚠ 不要自己加 save**：回滚只还原参数，**不得**顺手写 `1010h`——
持久保存必须是独立、需二次确认的人工动作。

### 修复 3：端序测试只断言首字节

**位置**：`device/tests/test_pdo.cpp:127`

**现状**（**主会话已用变异测试独立验证**）：
该行是唯一的字节级断言，只检查 `encoded.value().data[0]`。
主会话做了**精确变异**——把 4 字节字段的第 2/3 字节对调（首字节与第 1 字节不动），
**2225 条断言全部通过、0 failure**。

**为什么重要**：RPDO2 的**字段 0 就是目标位置 `0x607A0020`**。
这种错误在实机上的表现是「电机走到错误位置**且不报任何错**」。
往返断言（`DecodePdo(EncodePdo(v)) == v`）对**对称**错误是盲的。

**修法**：
1. **逐字节断言**，不要只查 `data[0]`。至少对 4 字节字段断言完整四字节，
   例如目标位置 `0x607A0020` 的线缆字节应是 `20 00 7A 60`（小端）。
2. **断言要能抓住"单侧错误"**——即只在 `Encode` 或只在 `Decode` 里改坏的情形。
   建议加一组**不对称**的期望值（把已知值编码后与手写的字节序列比对），
   而不是只依赖往返。
3. **写完之后自己验证一次**：按修复 3 的做法注入变异（4 字节字段第 2/3 字节对调），
   **确认新测试会失败**。把这一步的实际输出贴进报告——**没做变异的"我加了断言"不算完成**。

### 修复 4：`max_late_us` 的语义

**位置**：`device/src/canopen/sync.cpp:53-56`

**现状**：
```cpp
stats_.max_late_us = std::max(stats_.max_late_us, now - next_us_);
```
而发送 deadline 用的是 `next_us_ + period_us_`（第 68/69/73 行）。

**⚠ 这一条与前三条不同，需要你先判断、再动手。** 审计的原始表述是"基准不一致、Skip 时低报"。
主会话复核后认为**它不完全成立**：`now - next_us_` 确实是"tick 唤醒迟到量"，
与发送 deadline 是两个不同的量。**但问题真实存在，只是性质不同**：

- `max_late_us` 报的是**唤醒迟到**，而**现场判定 CSP 时序真正需要的是"发送是否赶在 deadline 之前"**；
- deadline 是 `next_us_ + period_us_`，所以**即使 `max_late_us` 很小，发送也可能已经超期**；
- 第 69 行已经检测了这种超期（`status = ECommandTimeout`）并计入 `failures`，
  但**没有任何统计量度量"超了多少"**——现场拿不到这个数。

**要做的事**：
1. **先把语义写清楚**（在注释里）：`max_late_us` 到底是哪一个量。
   保留它作为"唤醒迟到"是合理的，只要写明白。
2. **补一个"发送 deadline 余量"的度量**（或明确说明为什么不需要），
   让现场能回答"我离超期还有多远"。**上限/负数语义要想清楚**（超期时应为负）。
3. **不要破坏既有测试**（`test_sync.cpp` 有覆盖）。
4. 报告里写清你选择的语义与理由——**这条的核心是"命名与度量要对得上"，不是"改个减法"**。
