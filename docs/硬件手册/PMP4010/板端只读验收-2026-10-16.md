不只是声明——取证脚本包装了发送层，对每个发出的帧分类：

发出的 SDO 读请求（0x601 + 0x40）: 43
非读请求的帧: 0  []

另用**两种独立实现**交叉验证（工具自带的 `SdoClient` 与自写 `struct` 构帧），

## 二、PDO 默认映射（`CONTRACT.md §1.1` 的阻塞项）

12 条映射全部等于手册出厂值（`E06 10.1 表10-5`），8 个 COB-ID 亦同：

| PDO | COB-ID | 映射 | 与手册 |
| --- | --- | --- | --- |
| RPDO1 | 0x201 | 控制字 0x6040:00 (16) + 工作模式 0x6060:00 (8) | ✓ |
| RPDO2 | 0x301 | 目标位置 0x607A:00 (32) + 插补数据 0x60C1:01 (32) | ✓ |
| RPDO3 | 0x401 | 目标速度 0x6042:00 (16) + 0x60FF:00 (32) | ✓ |
| RPDO4 | 0x501 | 目标转矩 0x6071:00 (16) | ✓ |
| TPDO1 | 0x181 | 状态字 0x6041:00 (16) + 模式回显 0x6061:00 (8) | ✓ |
| TPDO2 | 0x281 | 实际位置 0x6063:00 (32) | ✓ |
| TPDO3 | 0x381 | 实际速度 0x606C:00 (32) | ✓ |
| TPDO4 | 0x481 | 实际转矩 0x6077:00 (16) | ✓ |

**结论**：周期路径（PDO）存在且是出厂默认状态，不必退化为 SDO 事务。
`1400:02` 传输类型 = 0x00（同步），`1005h` = 0x80 → 设备作 SYNC **消费者**。

**但「1 ms 周期」不成立**——带宽预算见 `docs/架构设计/实测基线.md §十`。
can-2 设计挂 8 个节点，位置环最小可行周期是 8 ms。

## 四、安全相关发现

### 4.1 软件限位被放开到接近 int32 全域

```
607D:01 下限 = -2147483628   （手册出厂 -65535）
607D:02 上限 =  2147483627   （手册出厂  65535）
```

驱动 A1 的值域校验**代码正确**（读限位、比对、越界拒绝、读失败也拒绝），
但在这台电机上**等于没有保护**：值只要落在 int32 内就放行。

**A1 修的是「无论限位是多少都照发」这个结构性缺陷；它不提供行程安全。**
真正的行程边界只能来自把 `607Dh` 写回合理值（整机调试时确定），
或上层配置里的行程护栏。

### 4.2 残留目标值

```
607Ah 目标位置 = 7800  计数 = 21.4 度
60FFh 目标速度 = 6553600 用户单位/s = 3000 rpm（正是额定转速）
6042h        = 0
6071h        = 0
```

**当前是安全的**：控制字 0、模式 0、bit4=0，三个条件同时成立，电机不可能运动。
驱动 `MoveTo` 也是先清 bit4 再发 `0x0F`→`0x1F`，使能序列（`0x06/0x07/0x0F`）
全程 bit4 为 0，没有任何路径会在使能时顺带触发运动。

**不清零的理由**（用户已确认）：清零并不消除危险——目标值 0 与当前位置
-1463 不同，谁触发 bit4 电机照样走 4 度。唯一安全的值是"等于当前位置"，
那需要每次运动后重写，没有意义。真正的防护是操作纪律（同一时刻只有一个
主站占用总线）。

**已加固的防护**：既然 `60FFh = 3000 rpm` 是残留值，而它在速度模式下会
生效，驱动现在**拒绝在速度模式（3）下使能**（提交 `581da9c`）。
理由与实现在 `pmp4010_driver.cpp` 的 `CanEnableInMode` 注释里。

### 4.3 心跳未启用

`1017h` = 0（出厂默认）。断线检测当前**无依据**——手册 §3.5.2 明写
「本设备只支持心跳」，未启用即没有断线通知。启用需要写 `1017h`，
属写操作，未执行。

## 五、手册与实测的冲突（**只报告，未改文档**）

设备对若干对象**有响应**，而手册对象字典**没有这些行**：

| 索引 | 名称 | `od.json` / `CONTRACT.md` 的说法 | 设备实测 |
| --- | --- | --- | --- |
| `1005h` | SYNC COB-ID | 「手册没有 1005h」 | **存在 = 0x80** |
| `1007h` | 同步窗口长度 | 「没有 1007h」 | **存在 = 0** |
| `1014h` | EMCY COB-ID | 「表10-5 无 1014h 行」 | **存在 = 0x81** |
| `100Ch` | 节点保护时间 | 「不支持节点保护」 | **存在 = 0** |
| `100Dh` | 节点保护倍数 | 「不支持」 | **存在 = 0** |
| `1006h` | 通信周期 | 「没有 1006h」 | 中止 `0x06020000` |
| `1016h` | 消费者心跳时间 | 「不支持」 | 中止 `0x06020000` |

手册侧核对（全文 grep 计数）：`1005H / 1006H / 1007H / 100CH / 100DH / 1016H`
**各出现 0 次**；`1014H` 只在 §3.4 正文出现 1 次，不在 10.1 表中。

**要紧的是区分两件事**：

1. **「手册没写」不等于「设备没有」**。手册的对象字典不完整，
   设备多实现了若干标准对象。这不构成驱动的缺陷——驱动的 OD 台账
   以手册为唯一来源，是仓库既定规则。
2. **「能读到一个对象」不等于「该功能被支持」**。`100Ch`/`100Dh`
   能读出 0，但手册 §3.5.2 明说「本设备只支持心跳」，且 `1016h`
   确实中止。所以「节点保护不可用」这个结论仍站得住，只是依据
   应当写成「手册声明 + `1016h` 中止」，而不是「`100Ch`/`100Dh` 不存在」。

**为什么值得记**：这三条（`1005h`/`1014h`/`100Ch`）在 `od.json` 里保持
`unverified`，而 OD 闸门是「全部 verified 才开」的单一布尔量。这意味着
**文档转换的完成度直接决定电机能否运动**——而那 6 条按定义永远不会
变成 `verified`（od.json 的 note 明确禁止伪造）。这是设计约束，
不是缺陷，但它在整机调试时会直接挡住运动验收，需要届时决定出路。

## 六、取证过程中主会话自己犯的错（记录在案）

三次字节序/位域错误，每次都是靠换一种独立实现重算发现的：

1. **SDO 请求的索引字节序写反**：`0x607D` 写成 `40 60 7D 01`（高字节在前），
   电机正确地回「对象不存在」，我一度以为与工具结果矛盾。正确是 `40 7D 60 01`。
2. **PDO 映射条目拆解弄反**：映射编码是大端语义的
   索引<<16 | 子索引<<8 | 位长，我按小端拆，一度以为映射只有 3 字节。
3. **SDO 的 n 位算法错**：`(cs >> 1) & 0x07` 应为 `(cs >> 2) & 0x03`，
   导致 `0x43` 被当成 3 字节，**所有 4 字节对象丢最高字节**。
   最终靠给解码器写自检（已知向量）才发现。

另外一次误报：我一度判断「agent 违反指令去 ssh 板子」——实际那 50 次
命中来自我 prompt 里的字面文本，实测工具调用 280 次、涉总线 **0 条**。
教训：粗筛关键词会把 prompt 自身算进去。

**结论**：工具自带的 `SdoClient` 一直是对的。自写解析器必须先过自检再用于取证。
