# PMP4010 驱动实现审查（2026-10-15）

**审查对象**：驱动填充 agent 的 C++ 驱动实现与 Python 运动命令（未提交的工作树）
**审查方式**：5 个独立维度 + 对抗性验证（10 个 agent，其中 5 个专职尝试推翻另 5 个的结论）
**审查结论**：**实现质量可用，但「验证通过」的声明不成立——两个 CI 闸门是红的**

---

## 一、最重要的一条：声明的验证结果不成立

驱动 agent 报告「验证通过：C++ ASan/UBSan 5/5、Python 运动测试 46 项、共享协议测试 160 项、打包测试 4 项」。

**这些数字本身都属实**（审查者逐条重跑，全部复现）。但报告**漏掉了两个必要的机检闸门**：

| 闸门 | 实测 | 后果 |
| --- | --- | --- |
| `check-manual-citations.sh` | **rc=1**（27 处违规） | CI 的 `Manual citations` 步骤会红 |
| `check-docs.sh` | **rc=1**（树中声称 `ui/` 不存在） | CI 的 `docs` job 会红 |

`check-manual-citations.sh` 的 27 处在 HEAD 基线是 0 处（实测：`git archive HEAD` 后同一脚本 rc=0），**是本次改动引入的**。

`check-docs.sh` 的 `ui/` 是**预存缺陷**（HEAD 上同样是 rc=1），但它让「机检全绿」的前提从一开始就不成立。

**唯一一处硬失败**：CI 会红。这与《硬件驱动开发路径.md》第 11 步「提交前机检必须全绿」直接冲突。

## 二、真缺陷（对抗性验证后全部 CONFIRMED）

### 2.1 [high] 目标位置与速度**没有任何值域校验**

`pmp4010_driver.cpp` 的 `MoveTo` / `SetTargetPosition` / `SetTargetVelocity` 直接把值写进 `607Ah` / `60FFh`，从不与 `607Dh`（软件限位）/ `6080h`（最大速度）比对。

审查者实测反例（在 `/tmp` 副本里，未改仓库）：

```
MoveTo(INT32_MAX)          -> ok=1, 发出 607Ah = 0x7FFFFFFF
SetTargetPosition(INT32_MAX)-> ok=1, 发出 607Ah = 0x7FFFFFFF
SetTargetVelocity(INT32_MAX)-> ok=1, 发出 60FFh= 0x7FFFFFFF
SetVelocity(INT32_MAX, Raise) -> 取反后写入 0x80000001
```

唯一存在的约束是**宽度**（`WriteObject` 里的 `item->width < 4` 检查，而目标位置宽度就是 4，不触发）和 `SetVelocity` 的「非负幅值」。

**od.json 自己写明**：607Ah 条目 note 原文「PP 模式里还受 607Dh 软件限位与 607Fh 最大轮廓速度约束」，607Dh 出厂值仅 ±65535。驱动一次都没做这个比较。

**当前无现场暴露**（`kOdVerified=false` 挡住了全部发帧路径），但对象字典一旦核对通过即生效。

### 2.2 [medium] `SetVelocity` 无上界拒绝

只拒绝 `value < 0` 与非法方向，非负幅值无上限。同一个越界值经符号取反后写入。

### 2.3 [medium] CiA 402 模式前置校验只做在两条路径上

读 `2002h:01h` 并要求为 0（CiA 402 模式）**只**做在 `EnableSequence` 与 `Home` 里。

实测（selector=4，即手册表10-6 的出厂值 NiMotion 开环）：

```
SwitchOn        ok=1 frames=2 read2002=0
EnableOperation ok=1 frames=3 read2002=0
Shutdown        ok=1 frames=2 read2002=0
QuickStop       ok=1 frames=2 read2002=0
FaultReset      ok=1 frames=4 read2002=0
Disable         ok=1 frames=2 read2002=0
Stop            ok=1 frames=2 read2002=0
Enable          ok=0 frames=1 read2002=1   ← 只有它读了
```

7 个直暴露原语全部绕过模式检查，向一台**未确认处于 CiA 402 模式**的驱动器写 CiA 402 控制字。od.json 的 `mode_select_manual_conflict` 条目原文就警告过这一点：「实机首次 status 必须先读 2002h:01h 确认，不能假定」。

Python 侧同形：`require_cia402()` 只在 `enable()` 与 `home()` 调用。

### 2.4 [medium] 驱动里的字符串对象白名单绕过 OD 台账

`StringObject` 把 `0x1008` / `0x1009` / `0x100A` 硬编进驱动，但 od.json 里**没有这三条**。后果：

- 它们不在「79 条 / 6 未核对」的台账里，工具打印的未核对清单不会提到它们。
- `ReadRaw` 的宽度校验写作 `if (result && item && ...)`，`item` 为 null 时**整条校验被跳过**，这三个对象的返回长度不做任何校验。

### 2.5 [medium] Python 共享层的分段上传**无界**

`tools/hwtui/canopen.py` 的 `_read_segmented` 是 `while True:`，唯一退出条件是服务端置末段位（或异常）。既无总字节上限，也无段数上限；C++ 同一条路径在 `canopen.hpp:88` 有限制。

实测：假总线持续回非末段应答时，2 秒内消费 755196 个段、累积 5286372 字节仍不返回。触发点是 `--scan --identity`（读 0x1008 字符串）。

（注：审查者纠正了一处夸大——增长的是进程内 `bytearray`，不落盘，不会占满根分区。）

### 2.6 [medium] C++ 与 Python 对同一字节的判定相反

`canopen.hpp:76` 用**硬编码** `0xF3` 掩码判加急上传应答，而生成物里的共享常量 `SDO_EXPEDITED_CS_MASK` 是 `0xE3`，Python 用的正是 `0xE3`。

枚举 256 个命令字，差异恰好 5 个：`0x42`（C++ 接受 / Python 拒绝）、`0x53/0x57/0x5B/0x5F`（Python 接受 / C++ 拒绝）。同一个从站、同一个字节，驱动与板端工具结论相反。

### 2.7 [medium] 迟到的同索引应答会污染下一次读

`Begin()` 只清 256 帧，超时后上一次的迟到应答留在队列里。实测：第一次 `Upload` 超时后，第二次读**采纳了第一次的陈旧值**。

对 `EnableSequence` 的具体后果：若陈旧值是 `0x27`（Operation enabled）而驱动器实际已故障，会误判已使能并跳过故障复位。`Home` 里专门用 `seen_incomplete` 防的「上次完成位」也会被同样方式击穿。

## 三、框架级缺陷（已修）

这五条会影响**后续每一个硬件**，所以由我（主会话）直接修掉，已提交 `34db468`：

1. **检查器漏检 `u` 后缀**：`\b0x[0-9A-Fa-f]{4}\b` 匹配不到 `0x1400u`（`4` 与 `u` 之间没有词边界），C++ 侧 7 处掩码完全没被查，而 Python 侧同一批值照报不误。已修：接受 `u/U/l/L` 后缀。
2. **生成物豁免只认一个生成器**：原实现只认 `gen-od.py` 的首行标记，另外两个生成器的产物不豁免——只要写出任何四位字面量就恒红。已修：改认标记的形状。
3. **同目录测试文件未豁免**：`tools/_test_<型号>.py` 漏网，本轮被报 23 处。已修。
4. **旁路守卫按「宏是否存在」判定**：`-DKM3_ALLOW_UNVERIFIED_OD=0` 也算已定义，本想**关闭**旁路反而打开了它。已修：判真值。三个方向都验证过（默认编不过 / =1 编过 / =0 编不过）。
5. **生成物手册路径用小写型号**：写出 `docs/硬件手册/pmp4010/README.md`，在 Linux 上不存在——一条**指错路**的注释。已修：按磁盘实际目录名解析。

## 四、确实成立的声明（不必怀疑）

审查者逐条核对，以下**都成立**：

- **未核对 OD 时零字节发出**：25 个 `GuardTransmit` 调用点覆盖全部 public 发帧方法，`kOdVerified=false` 时首条即拒绝并发零帧。测试断言的是**总线上的帧数**，不是返回码。
- **三条准入闸门齐备且 OD 闸门在最前**：`--motion` 顺序正确，`--i-know-rt-is-running` 不能绕过 OD 闸门。
- **未接入 RT 线程**：驱动内无 `new`/`malloc`/日志格式化/锁等待/`sleep_for`。
- **SDO 报文组装正确**：COB-ID、命令字选择、n 位编码、小端、toggle 翻转、索引回显、中止码，逐条核对无误（1/2/3/4/9/16/64 字节各路径实测）。
- **CiA 402 取值全部取自手册**：使能序列 `0x06/0x07/0x0F`、状态字掩码 `0x6F/0x4F`、模式码 `{1,2,3,4,6,7,8,9,10}`、回零方法 17~30/35、PP 触发 `0x1F`——都能追到 E06 表4-2/表4-3/表6-3/表6-8/表6-9/表6-19，**没有一处「手册没写却编了个值」**。
- **未修改 od.json**。
- **未使用任何未核对条目发帧**。
- 测试数字属实（ctest 12/12；ASan/UBSan 5/5；Python 46 项；共享协议 160 项；打包 4 项）。
- **TSan**：报告说「因宿主内存映射错误未能运行」属实；审查者发现 `setarch -R` 可绕过，thread 模式下 `ctest` 全绿 12/12。

## 五、待办（交回驱动 agent）

### 5.1 必须修（安全相关）

1. **加值域校验**：`MoveTo` / `SetTargetPosition` / `SetTargetVelocity` 在发帧前与 `607Dh` / `6080h` 比对，越界拒绝。不把兜底交给驱动器。
2. **模式前置校验提到公共入口**：`GuardTransmit` 或等价处统一检查 `2002h:01h == 0`，而不是只在 `Enable` / `Home` 里做。
3. **字符串对象进 OD 台账**：把 `0x1008` / `0x1009` / `0x100A` 写进 od.json（带 cite），删掉驱动里的白名单；同时修 `ReadRaw` 里 `item` 为 null 时跳过宽度校验的问题。

### 5.2 应当修（一致性）

4. **位掩码进共享层**：把 `HOMING_TARGET_REACHED`(bit10) / `HOMING_ATTAINED`(bit12) / `HOMING_ERROR`(bit13) 加进 `tools/hwtui/canopen_wire.json`（cite 写 E06 表6-19），跑 `gen-canopen.py` 重新生成，两侧改用共享常量。
5. **工具改用共享 CiA402 常量**：`pmp4010.py` 里的 `0x06/0x07/0x0F/0x4F/0x6F/0x1400/0x2000` 等换成 `_canopen.CIA402_*`。这同时消除检查器报的 11 处和「两份真相」。
6. **Python 分段上传加上限**：与 C++ 的 `Payload::kCapacity / 7` 对齐。
7. **C++ 加急应答掩码用共享常量**：`0xF3` → `SDO_EXPEDITED_CS_MASK`，去掉 `cs == 0x42u` 这个 Python 不认的分支。
8. **`Begin()` 的陈旧应答清理**：超时后清空属于该节点与索引的迟到帧，或在读回时校验时间戳。

### 5.3 可以稍后

9. `--nmt` 的闸门顺序与 `--motion` / 文件头声明统一。
10. `counts_per_unit` / `zero_offset_counts` / `heartbeat_period_ms` 三个字段已声明但全仓无读取点——要么接通，要么删掉（字段存在会让人以为换算已生效）。
11. `actual_velocity_counts` 的单位取决于 `2006h:12h`，驱动未读该选择器就把值当计数用。
12. `EnableSequence` 里一处 `uint32_t` → `uint16_t` 隐式窄化，触发 `-Wconversion` 告警。
13. `Home` 完成判据用 bit10 与 bit12 的**合取**，而手册把两者分列——比手册更严，属自定判据（不算缺陷，但应说明理由）。
