# TSan 条件变量等待追因

旧完整 PTY 的 `pty-tsan-final/reason.terminal` 保留了首个告警：`Drain` 在同一 `mutex_` 下读取事件队列，`Publish` 在同一 `mutex_` 下写入，但 GCC 11 TSan 同时报 double lock 和 race。Worker 在线程构造函数体中启动，成员均已完成初始化，未发现队列绕锁访问。

本机 `libstdc++` 11 的 `<condition_variable>` 对 `steady_clock::wait_until` 调用 `pthread_cond_clockwait`。`libtsan.so.0` 动态符号中只有 `pthread_cond_wait` / `pthread_cond_timedwait` 拦截器，没有 `pthread_cond_clockwait`。本目录 `runtime.json`、`tsan-symbols.txt` 和 `minimal-symbols.txt` 保留本机命令及符号证据。

最小对照程序 `compare.cpp` 中读写相同整数并共用同一 mutex，每组100次：

| 等待方式 | 结果 | 原始命令/退出/日志 |
| --- | --- | --- |
| std::condition_variable + steady_clock::wait_until | rc66，double lock + race | `../tsan-cv-steady.*` |
| std::condition_variable + system_clock::wait_until | rc0，无告警 | `../tsan-cv-system.*` |
| CLOCK_MONOTONIC条件变量 + pthread_cond_timedwait | rc0，无告警 | `../tsan-cv-pthread.*` |
| 同上，但故意取消读线程mutex | rc66，真实race仍被报告 | `../tsan-cv-unsafe.*` |

这证明本机旧等待路径使 TSan 丢失了条件等待释放/重取 mutex 的同步关系。没有将告警直接当作假阳性，也未添加 suppression、`no_sanitize` 或针对 sanitizer 的条件编译。

修复只将 Worker 的限时等待改为所有构建共用的 `MonotonicWakeup`，使用 `pthread_condattr_setclock(CLOCK_MONOTONIC)` 和 `pthread_cond_timedwait`。保留 std::mutex 保护的命令/结果队列、通知立即唤醒、spurious wake predicate循环和 steady截止期限；不改为wall clock，也不改CAN串行规则。文件日志线程原本使用无期限的普通 `condition_variable::wait`，没有触发相同路径，保持原实现。

修复后同一个TSan二进制连续5次真实reason PTY，rc0、25断言、零TSan WARNING、termios完整恢复，见 `../tsan-reason-fixed-minimal/`。完整host/ASan/TSan矩阵由构建worker单独记录，不能用此最小复现替代。
