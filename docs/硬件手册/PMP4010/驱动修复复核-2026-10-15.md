## 二、逐项复核

### A1 值域校验 ✓ 且比报告更完整

校验落在 `WriteValue`（`pmp4010_driver.cpp:275`）——**所有数值写入的唯一汇聚点**。

- `target_position` → `RequirePositionInRange(:293)`：读 `607Dh:01h`/`607Dh:02h`，
  越界返回 `EInvalidRequest`，**上下限读失败时同样拒绝**（fail closed）。
- `low > high` 时返回 `EInvalidConfig`——配置本身矛盾也拒绝，不是简单放行。
- **通用写入绕不过去**：`WriteObject`（按索引）与 `SdoWrite` 都走 `WriteValue`，
  实测测试用例 `position_limits_fail_closed_inclusive_and_generic_writes_cannot_bypass`
  正是钉这一点。
- 速度：`SetTargetVelocity`/`SetVelocity` **无条件返回 `EInvalidConfig`**。

**判断**：速度全部拒绝是正确的。E06 §5.2 要求先读 `608Fh`/`6091h` 才能把
「用户单位/s」换算成 `max_motor_speed` 的 rpm，驱动没有这条链。按 prompt
「不许拍一个系数进去」，拒绝是唯一诚实的做法。

**但这是待办不是终态**：PV 模式（mode 3）是手册支持的，启用前必须先实现
`608Fh`/`6091h` 的读取与换算。README 已记为待办。

### A2 模式前置校验统一 ✓ 且覆盖所有九条原语

`RequireCia402(:288)` 被 `WriteValue` 的 `controlword` 分支调用，而
**所有控制字写入都经 `Control()` → `WriteValue(node,"controlword",…)`**。

实测测试 `all_controlword_primitives_require_cia402_and_selector_failure_denies`
遍历九条原语（Enable/Disable/Shutdown/SwitchOn/EnableOperation/QuickStop/
FaultReset/Stop/Home）× 三种失败态（selector=4 / 中止码 / 静默超时），
全部断言**运动写入计数为 0**。

**一处设计后果需要注意**：`QuickStop`/`Stop` 现在也要求先成功读 `2002h:01h`。
selector 读失败或节点被隔离时，快速停机**发不出去**。这在当前是对的
（连控制字索引都不可信时，0x02 可能被解读成别的东西），且 `CONTRACT.md:195`
已声明「现场停机由独立安全设计负责，不得宣称停服务就能安全停机」。
但它意味着**驱动不提供紧急停机**——这一点必须在现场安全设计中落实。

### A3 字符串对象进台账 ✓ 且白名单彻底删净

- `od.json` 新增 `device_name(0x1008)` / `hardware_version(0x1009)` /
  `software_version(0x100A)` / `software_position_limit_max(0x607D:02)`
  → 79 变 83 条，77 verified / 6 unverified。
- `StringObject` 白名单**已删除**（出现次数 0）。
- `ReadRaw(:147)` 现在对未知对象**直接拒绝**（`if (!item) return EInvalidRequest`），
  不再是「item 为 null 时跳过校验」。
- 定长与变长分别校验：`item->variable_length ? size > item->width : size != item->width`。
- `ReadString(:196)` 额外要求 `item->variable_length`——按索引读字符串不再可能。

### B1 位掩码进共享层 ✓

- `canopen_wire.json` 新增 `CIA402_HOMING_TARGET_REACHED(0x400)` /
  `CIA402_HOMING_ATTAINED(0x1000)` / `CIA402_HOMING_ERROR(0x2000)` /
  `CIA402_START_HOMING(0x1F)`，**每条都带出处**（E06 6.7.3 表6-19、4.1.2 表6-18）。
- 两个生成物已重新生成，C++ 与 Python 两侧**都无残留裸字面量**
  （`grep -c '0x1400\|0x2000'` 两侧均为 0）。
- 检查器那 11 处违规自然消失——没有给检查器加豁免后门。

### B2 加急应答掩码统一 ✓

改用共享常量，去掉 `cs == 0x42u` 分支。测试
`all_upload_command_bytes_match_independent_acceptance_table` 用**独立的
验收表**覆盖全部 256 个命令字，两实现被同一份数据钉住。

### B3 分段上传加上限 ✓

Python `SdoClient` 与 C++ 对齐容量限制。

### B4 陈旧应答隔离 ✓ 但引入一处新缺口

**设计正确**：超时且**已实际发帧**（`transmitted_`）时才置隔离，
`Begin()` 在隔离态直接返回 `EDeviceBusy`。注释明确写出为什么不能靠
「清队列/NMT/等待/新建连接」证明恢复——**SDO 没有事务序号，无法区分迟到应答
与新应答**。这是正确的推理。

**新缺口**：`ConfirmExternalRecovery` 是解除隔离的**唯一入口**，
但 `pmp4010_driver.hpp` **没有暴露任何调用它的方法**（`grep` 零命中），
驱动器也没有为 SdoClient 提供访问器。当前只有测试直接持有 `SdoClient`
才能调用它。

**后果**：一次 SDO 超时后，该节点在**该进程存活期内永久不可用**。
这比"旧应答被误用"安全得多，但它是**可用性缺陷**，且现场表现是
「电机突然再也不响应，重启才恢复」——排查成本高。

**建议**（不阻塞本次提交，但应尽快）：
- 在 `Pmp4010Driver` 上暴露 `IsQuarantined(node)` 与
  `ConfirmExternalRecovery(node)`，并在 `NodeState` 或
  `DriverStats` 里加一个「本节点处于隔离」的可观测标志；
- 或者在 `CONTRACT.md` 里写明「隔离后需重启进程」是**有意选择**而非遗漏。

   要启用必须先实现 `608Fh`/`6091h` 换算链。
