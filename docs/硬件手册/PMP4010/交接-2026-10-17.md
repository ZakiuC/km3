### 2.2 速度换算链：Python 有一半，C++ 一点没有

**Python 侧**（`pmp4010_position.py:207`）——只有**正向检查**，没有反向换算：

```python
or args.velocity * Fraction(cal['gear_ratio']) / Fraction(cal['resolution']) * 60
   > limits['max_motor_speed']
```

这是「用户单位/s → rpm」，用来跟 `6080h`（电机最大转速，rpm）比。
**反过来的 `rpm → 用户单位/s` 不存在**，也就是说没有任何地方能把一个 rpm
数值变成要写进 `60FFh` 的用户单位值。

**C++ 侧**——三个入口全部无条件拒绝：

| 函数 | 位置 | 返回值 |
| --- | --- | --- |
| `SetTargetVelocity` | `pmp4010_driver.cpp:465` | `EInvalidConfig` |
| `SetVelocity` | `pmp4010_driver.cpp:502` | `EInvalidConfig` |
| `WriteValue("target_velocity")` | `pmp4010_driver.cpp:215` | `EInvalidConfig` |

三处注释都写着同一句理由：`E06 §5.2` 需要 `608Fh`/`6091h` 的实时换算，
而驱动没有。

**关键的不对称**：Python 能读这四个标定值，C++ 不能。

```
Python: od.json 的 user_unit_scale 条目带 motion_objects 子表
        -> encoder_increments       0x608F:01  uint32
        -> encoder_motor_revolutions 0x608F:02  uint32
        -> gear_motor_revolutions    0x6091:01  uint32
        -> gear_output_revolutions   0x6091:02  uint32
        pmp4010_position.py 的 calibration() 直接读这四项。

C++:   gen-pmp4010-access.py 只收录 `status == verified and index is not None
       and sub is not None` 的条目。user_unit_scale 的 sub 是 null（它是
       结构型条目，真正的地址在 motion_objects 里），所以被跳过。
       结果：kAccess 表里根本没有 608F/6091。
```

### 2.3 换算公式（手册原文，已核实）

`od.json` 的 `velocity_scale` 条目引用 E06 §5.2：

```
电机轴转速(rpm) = 驱动轴转速(用户单位/s) × 传动比(6091h) × 60 ÷ 编码器分辨率(608Fh)
```

其中 `608Fh = 608F:01 / 608F:02`（编码器增量 / 电机转数），
`6091h = 6091:01 / 6091:02`（电机轴转数 / 驱动轴转数）。

**手册只给了这一个方向。** 反向（rpm → 用户单位/s）是代数推出来的：

```
用户单位/s = rpm × 编码器分辨率 ÷ 传动比 ÷ 60
```

**这不是手册原文，是代数反演。** 实现时要在注释里写清这一点。

**交叉验证过**（`target_velocity` 条目的 note 里有记录）：
E06 §6.5.5 举例「`60FFh = 50000` → 电机 300 rpm」，
在默认 `608F = 10000/1`、`6091 = 1/1` 下 `50000 ÷ 10000 × 60 = 300`，自洽。

**本机实测标定值**：`608F = 131072/1`、`6091 = 1/1`。按此换算：
`60FFh = 50000` → `22.888 rpm`；`60FFh = 6553600` → **恰好 3000.000 rpm**（额定转速）。
后者是现场残留值，正是模式 3/9 被挡住的原因。

## 三、任务 #1：速度换算链

### 3.1 目标

让「用户单位/s ↔ rpm」的换算在两个语言里都能用，且**只有一份定义**。

### 3.2 必须先做的设计决定（**做之前先回答**）

**换算函数放在哪？**

当前 Python 和 C++ 各写各的，已经漂移过一次（mode 9 就是漂移产物）。
三个选项：

- **A**：C++ 成为唯一实现，Python 通过某种方式调用 —— 成本高，且 Python 工具
  是独立脚本，不能依赖 C++ 二进制
- **B**：两侧各写一份，但**加一组共享测试向量**（固定的标定值 + 输入 + 期望输出），
  两边跑同一组向量比对。成本低，能挡住漂移
- **C**：从 `od.json` 或某个共享 JSON 生成两侧代码（像现在的 `gen-od.py`）

**建议 B**，理由是成本与收益匹配。但**这是人类的决定，不要自行选**。
把这三种方案的代价写清，报给人类。

### 3.3 要改的地方（若是 B）

**Python**（`pmp4010_position.py`）：

```python
def calibration(values):   # 已存在，返回 resolution / gear_ratio
```
在此之上加：

```python
def velocity_to_unit(rpm, cal):        # rpm -> 用户单位/s
def unit_to_velocity(units_per_s, cal): # 用户单位/s -> rpm
```

注意：
- 用 `Fraction`，不用 float。项目里已有这个惯例（`Fraction(cal['gear_ratio'])`）
- 结果为整数时要明确取整方向。**不要静默截断**——写出去的 `60FFh` 与用户
  预期不符时，现场最难查的就是「差一点点」
- 除零、负数、非有限值要显式处理

**C++**（`pmp4010_driver.cpp`）：

1. **先让 C++ 能读 `608F`/`6091`**。这需要改 `gen-pmp4010-access.py`：
   让它也展开 `motion_objects` 子表（Python 侧已经这么做了）。
   改完重新生成 `od_access_generated.hpp`，`--check` 必须过。
2. 在 `SetTargetVelocity` / `SetVelocity` / `WriteValue("target_velocity")`
   三处接上换算。三处**必须调用同一个函数**，不要各写一遍。
3. 换算前**必须实读**四个标定值（它们是「停机生效」的可写参数，
   不能缓存成常量）。

### 3.4 验收

**共享测试向量**（两侧跑同一组，贴输出）：

| 标定 `608F/6091` | 输入 | 期望 |
| --- | --- | --- |
| `10000/1`, `1/1`（默认） | `50000` 用户单位/s | `300 rpm` |
| `131072/1`, `1/1`（本机） | `50000` 用户单位/s | `22.888 rpm` |
| `131072/1`, `1/1`（本机） | `6553600` 用户单位/s | `3000.000 rpm` |
| 任意 | `0` | `0`（两个方向都是） |
| `6091 = 3/1`（减速比 3） | 反向验算 | 与正向互逆 |

**互逆性测试**：`unit_to_velocity(velocity_to_unit(x)) == x`，在整数范围内抽样。

**边界**：`608F:02 = 0`、`6091:02 = 0`（除零）、负数、超过 `int32` 范围。

**四处必须同时改。** 只改一处就是这次 mode 9 漏洞的重演。

### 4.3 放开之前必须想的：残留值问题还在

即使换算链落地，**`60FFh` 里的残留值仍然是 3600 rpm 级别的**。
换算链让你能**写**正确的值，但挡不住「别人写了一个值，然后你使能」。

**必须先确立一条规则**，否则放行使能就是在复制原来的问题：

> 速度模式下使能之前，**必须先写一次 `60FFh`**（哪怕是 0），
> 确认写读回一致，然后再发使能序列。

这条规则要写进代码注释和测试。**这是本次放开的核心安全不变式**，
比换算公式本身更重要。

### 4.4 验收

- 模式 2/7 仍然拒绝（理由不变：终值不同）
- 模式 3/9 在**换算链可用且标定值实读成功**时可以使能
- 标定值读失败时**拒绝使能**（不能拿默认值凑）
- 使能前 `60FFh` 未写过的场景**必须有测试**证明被拒绝

## 六、任务 #4：OD 闸门的终局（**人类决策**）

### 6.1 问题

闸门是单一布尔量：**任何一条非 verified 就全拒**。
而其中几类按定义永远进不了 verified（见 §2.5）。

后果：**整机调试时运动验收被永久挡住**。这不是"更安全"，是"无法推进"。

### 6.2 三个方案（给出代价，不选）

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| A | 保持现状 + `--od-gaps-bypass` 人工放行 | 每次调试都要写理由；跨会话不记忆；人可能不看理由就放行 |
| B | 按条目分级：`unsupported`（本设备不支持）/ `host_policy`（主机策略）/ `missing`（真的缺） | 要改 `od.json` 的 status 语义、`gen-od.py`、所有读 status 的地方；改动面大 |
| C | 闸门只挡「会影响本次动作」的条目（例如位置运动不看 EMCY） | 要建立「动作 → 依赖条目」映射；映射本身可能错 |

**建议由人类定，agent 只提供方案。** 我的倾向是 B——它把问题从「不可满足
的条件」变成「可满足的分类」，且一次改完永久受益。但这需要人类同意改
`od.json` 的 status 语义，那是数据格式变更。

## 九、已知的坑

| 坑 | 说明 |
| --- | --- |
| 生成器拼接 | `for g in "gen-od --model pmp4010"; do python3 $g.py` 会截断成 `gen-od`，产生假 rc=0。逐个写全 |
| `grep -c` 返回 0 | 退出码 1，会截断 `&&` 链 |
| TSan | 必须 `setarch -R` |
| `608F`/`6091` 是停机生效 | 不能缓存，每次用前实读 |
| `606C` 单位可切换 | `2006h:12h = 0` 是 rpm，`= 1` 是用户单位。显示前读一次 |
| `607C` 不是设零点 | 它是原点偏移，只在回零后生效，不改变 `6064` |
| `bit15` 不是标准状态位 | 4.1.3 未定义它，只在回零结果里按「手册散见说法」引用 |
| 模式 2/7 与 3/9 理由不同 | 前者是使能终值，后者是换算链。别混成一句话 |
