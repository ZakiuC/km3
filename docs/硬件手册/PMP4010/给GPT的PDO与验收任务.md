# 给 GPT 的任务：PDO 收发 + 参数写入工具 + 运动验收（2026-10-16 第二批）

## 任务目标

三件事，**按依赖顺序做**，每件做完自己跑验收再进下一件：

1. **任务 A：PDO 收发**（纯代码，不碰电机）
2. **任务 B：参数写入工具**（建工具 + 干跑验证，**不在板上执行持久写**）

把现在能用的异步通道换成没人喂的同步通道，还要持久写 EEPROM。所以 B 建好、验好、**不执行**。

- **⚠ 该后端已设 `CAN_RAW_LOOPBACK = 0`** —— 因此**本机 `candump` 看不到自己发的帧**，
  别再拿 `candump` 当发帧证据，改用**接口计数差分**

### 1.5 写参数的真实风险（**读清楚再动手**）

**60C2h 与 1400h/1800h 的传输类型都是「停机生效」**（手册 10.3 表10-7 明写）。
这意味着：**写错了不会让电机当场失控** —— 参数在**下次上电前不生效**，
而 CANopen 通信不依赖这些参数，所以 **SDO 永远救得回来**。

**但这不等于可以省掉备份**：
- `1010h:01h` 写 `0x65766173`（"save"）才会持久化到 EEPROM；**不写就不持久**
- EEPROM 擦写寿命有限，**不要反复 save**
- **上电前必须把当前值完整备份**，否则回滚只能靠猜

## 二、任务 A：PDO 收发（纯代码，不碰电机）

### A.1 要实现什么

在 C++ 侧实现 **RPDO 发送**与 **TPDO 接收**，让同步模式有意义。

**必须先读**：`canopen_sync.hpp` / `sync.cpp` 看上一批怎么做的（预构造帧、绝对时钟、eventfd 唤醒停止），
**沿用同一套路**，不要另创一套。

### A.2 关键设计问题（**必须判断并写明理由**）

1. **RPDO 发送在哪个线程？** 上一批 SYNC 选了独立非实时线程（路 B）。RPDO 的时序要求比 SYNC 更紧
   （位置指令的节拍一致性直接影响 CSP 跟随），**沿用路 B 是否仍成立？** 若沿用，说明抖动是否可接受；
   若改路 A，必须给出「凭什么不阻塞 RT」的可核查论证，**不接受"实测没阻塞过"**。

2. **SYNC 与 RPDO 的先后顺序**：CANopen 语义是「收到 SYNC 后，从站把 RPDO 最新数据更新到应用」。
   因此**同一周期内必须 SYNC 在后、RPDO 在前**（否则该周期的数据要等下一个 SYNC 才生效，
   等于凭空多一个周期延迟）。**这个顺序必须实现且有测试**，写进注释。

3. **TPDO 接收**：`0xFF`（异步）时 TPDO 数据变化就发；改成 1~240 后按同步帧计数发。
   接收侧不能假定「每周期必有 TPDO」——**必须容忍缺失**，不得因此阻塞或报错。

### A.3 硬要求

- **不得硬编码 COB-ID / 节点号 / 周期**，全部来自配置与 `od.json` 生成的常量
- **接收路径不得分配内存**，用预分配缓冲
- **帧长度必须校验**：映射了 2 个对象（如 RPDO1 = 16 位 + 8 位 = 3 字节），
  发错长度**不会报错但会静默错位** —— 必须按 `1600h:00h` 的条目数算出期望长度并校验
- **字节序**：CANopen PDO 数据是**小端**（与 SDO 一致）。本项目在解码上犯过三次字节序错误
  （见 `板端只读验收-2026-10-16.md` §六），**必须有往返测试**
- 不得调用任何 SDO 写、不得发 NMT

### A.4 验收

1. 构建（宿主 + aarch64 交叉，工具链绝对路径）
2. 三套 CTest（host / ASan / TSan；TSan 需 `setarch -R`）**贴实际输出**
3. 四个机检闸门 rc=0
4. 新增测试覆盖：帧长度校验、字节序往返、SYNC/RPDO 顺序、TPDO 缺失容忍、无分配
5. **可选上板**：只发 RPDO，用接口计数差分证明帧上了总线（**不要用 candump**）

## 三、任务 B：参数写入工具（建工具，**不在板上执行**）

### B.1 背景

Python 工具目前**完全没有写入路径**（`--raw` 只监听，`--motion` 只做 CiA402 使能/失能）。
C++ 标准层有 `Download`，Python 侧没有任何 download。

### B.2 要实现什么

在 `device/drivers/pmp4010/tools/pmp4010.py` 加一个写入子命令，具备：

1. **备份**：把待改对象（含全部 RPDO/TPDO 传输类型、`60C2h:01h/02h`、`1010h` 相关）
   的**当前值**读出并存成 JSON 文件，含时间戳、设备身份（`1018h` 四个字段）、
   接口名、位速率。**回滚脚本必须能以这份备份为输入**。
2. **干跑（默认）**：打印将要写什么，**不实际写**。必须显式 `--apply` 才写。
3. **逐条校验**：写入前读一次、写后**再读回确认**，不一致就报错并停止。
4. **范围校验**：写入值必须落在 `od.json` 记录的合法范围与宽度内，越界在**发帧前**拒绝。
5. **OD 闸门**：与 `--motion` 同样先过 `refuse_motion()`（**不要为它开后门**）。
6. **保存单独一步**：`1010h:01h = 0x65766173` 必须是**独立的、需二次确认**的动作，
   不得与其他写入混在一次调用里。
7. **回滚命令**：读备份文件后把原值写回（同样默认干跑）。

### B.3 要写的具体值（写进工具文档，**不执行**）

| 对象 | 现值 | 目标值 | 依据 |
| --- | --- | --- | --- |
| `1400h:02h`~`1403h:02h` | `0xFF` | **`0x00`**（同步非循环）| 厂家要求；RPDO 类型 0 = 收到一个 SYNC 就更新 |
| `1800h:02h`~`1803h:02h` | `0xFF` | **`0x00`** | 同上，TPDO 侧 |
| `60C2h:01h` | `20` | 见下 | 插补时间常数 |
| `60C2h:02h` | `−1` | 见下 | 插补时间指数 |

**`60C2h` 的取值必须自己算并说明**：目标 `t × 10^n` 与 SYNC 周期（4 ms）一致。
注意本机 `n` 存储为 `0xFF`（有符号读作 `−1`），**写的时候要按 Int8 写**。

否则出问题分不清是哪个引起的。**把这个分批建议写进工具的输出。**

## 九、容易踩的坑

1. `60C2h:02h` 存的是 **Int8**，`0xFF` 读作 `−1`。写的时候别按 uint8 处理。
2. `0x1400` 与 `canopen_consts.py` 里的常量可能带整型后缀（`0x1400u`），
   正则匹配会漏 —— 本项目踩过。
3. `config.cpp` 的 CAN 端点 JSON 名是 `iface`，C++ 成员是 `device`；两者不一致是**故意的**。
4. 施工工具链路径**必须绝对**，相对路径会报 "Could not find toolchain file"。
5. TSan 在当前内核上**必然**报 `unexpected memory mapping`，用 `setarch -R` 才是真结果。
6. **不要用 `sleep_for` 做周期**，用绝对单调时钟推进。
7. 报数必须报实测 —— 本项目出过"说全绿但两个闸门是红的"（git log `2884dd1`）。
