# 硬件手册与通讯协议

本目录存放**厂家资料**，是硬件驱动的唯一事实来源。
源码里的每一个寄存器地址、对象字典索引、标度因子，都必须能追溯到这里的某份文件。

## 为什么单独成目录

`docs/架构设计/` 是**我们的设计**，本目录是**厂家的定义**。两者性质不同：

- 设计会变，厂家协议不会（除非换硬件）。
- 设计文档里不该出现"PMP4010 的对象字典 0x6040 是控制字"这类厂家事实——
  那会让设计文档随硬件型号漂移，而这类事实应由驱动代码引用本目录的资料。
- 硬件一旦更换或加装，只需新增一个子目录，不触碰设计文档。

因此规则是：**设计文档写"依据某手册的某节"，不复制手册内容**。

## 目录约定

```
docs/硬件手册/
├── README.md                本文件
└── <型号>/                   一个硬件一个目录，目录名用型号，不用中文别名
    ├── README.md             该硬件的资料索引与**未确认项**清单
    ├── *.md / *.pdf          操作手册、接线图说明、参数表
    └── 协议/                  通讯协议原文
        ├── *.md              报文格式、对象字典、EDS/DCF 说明
        └── *.eds / *.dcf     若厂家提供电子数据表，原样放这里
```

目录名用**型号**而非"机身抬降电机A"：型号是厂家事实，别名是我们的叫法，
同一个硬件在不同文档里可能叫不同名字，用别名做目录名会让引用失稳。

## CAN 端口编号（用户明确纠正过，勿再漂移）

硬件清单里的 `CAN-x` 指**主板 CAN 的第 x 个口**：

| 清单写法 | 内核接口 | 逻辑名 | 说明 |
| --- | --- | --- | --- |
| CAN-1 | can0 | can-1 | 主板第一个 CAN 口 |
| CAN-2 | can1 | can-2 | 主板第二个 CAN 口 |
| usb转can模块-1 | can2 | usb-can-1 | **USB 转 CAN 模块，不是 CAN-2** |

**陷阱**：内核里的 `can2` 是 USB 转 CAN 模块，而清单里的「CAN-2」是主板 `can1`。
下标差一位，接线与配置写错就会对错总线，且症状是「电机不动」这类最难反查的故障。
唯一权威表见 `docs/架构设计/设备端程序架构.md` §2.1.3。

> 来源：用户原话——「硬件清单里写的CAN-x：指主板 CAN 的 x 口，
> 也就是说 can-1 指的是第一个口就是 can0，而 can-2 才是 can1」。

## 放进来之后会发生什么

1. 我会读它，把其中**可编程的事实**提取到驱动的 profile 文件里
   （对象字典索引、控制字/状态字位定义、工作模式码、标度）。
2. `README.md` 里那份"未确认项"清单会逐条消解，并注明依据的手册章节。
3. 驱动里的占位值（当前标着 `// 待手册确认`）被真实值替换，同时补上对应测试断言。

**不要把手册内容复制进 `docs/架构设计/`**：那会造成两份真相，
且换硬件时必然漏改一处。
