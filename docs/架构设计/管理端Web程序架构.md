# 管理端 Web 程序架构

管理页面（`../前后端/功能清单.md` §二 管-F01 至 管-F06）是**浏览器应用**，
与 Android 控制台不是同一工程、不是同一技术栈、不是同一运行环境。

本文件是该工程的**设计权威**。实现细节不在本文档，见 `admin-web/`。

## 一、定位与边界

### 1.1 它做什么

| 能力 | 对应需求 | 依赖的服务端接口 |
| --- | --- | --- |
| 总览 | 管-F01 | `GET /analytics/overview` |
| 工时统计 | 管-F02 | `GET /analytics/workhours` — **口径未定，见 §七** |
| 传感器历史 | 管-F03 | `GET /devices/:id/sensors/:type/history` |
| 日志查询与实时流 | 管-F04 | `GET /logs`、`GET /devices/:id/logs`、WS `log.<device_id>` |
| 用户与邀请 | 管-F05 | `GET/POST /users`、`POST /users/invite` |
| 固件与 OTA 下发 | 管-F06 | `GET/POST /firmware`、`POST /firmware/:id/deploy` |

### 1.2 它不做什么（重要）

**管理端不实现运动控制命令下发。**

原因不是"暂时没做"，而是设计上的排除：`通信协议规范.md` §7.2 规定命令由
**用户侧私钥**签名（Ed25519），私钥只存在于 Android App 的 Keystore 中。
浏览器无法提供等价的密钥保护：
WebCrypto 的私钥虽可标记为不可导出，但它仍受制于同源脚本，且会随浏览器配置、
设备更换、清理站点数据而丢失。把控制机器人的签名能力搬到浏览器里，
是用可操作性与安全性的双重代价换一点便利。

因此职责划分是：

| 动作 | 管理端（Web） | 控制台（Android） |
| --- | --- | --- |
| 查看状态、历史、日志 | ✓ | ✓ |
| 用户、角色、邀请 | ✓ | ✗ |
| 固件上传与下发 | ✓ | 查看进度 |
| 运行配置修改 | ✓ | ✓ |
| **运动控制命令** | ✗ | ✓ |
| 紧急停止 | ✗（不排队，见协议 §8.1） | ✓ |

紧急停止不在管理端提供：它是安全关键路径，必须由现场操作员的设备发起，
经过浏览器中转只会增加不可控延迟与一个额外的失效点。

### 1.3 与三端的关系

管理端是**第四类客户端**，只与服务器端通信（REST + WebSocket），
不直连设备，不参与路径 A/C/D。设备在管理端眼里永远是"服务器上的一个资源"。
这样管理端不需要实现帧编解码、不需要隧道、不需要挑战应答，
也不需要理解设备端的任何实时约束。

## 二、技术栈

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 语言 | TypeScript 5.x（`strict`） | 接口契约来自服务端文档，类型是唯一能在编译期发现契约漂移的手段 |
| 框架 | Vue 3（Composition API + `<script setup>`） | 见 §2.1 |
| 构建 | Vite | 原生 ESM 开发服务器，构建产物是纯静态文件 |
| 路由 | Vue Router 4 | 官方配套 |
| 状态 | Pinia | 官方配套，无额外决策 |
| UI 组件 | Element Plus | 中文文档完备，表格/表单/日期范围选择是管理后台的主要工作量 |
| 图表 | ECharts 5（按需引入） | 时序数据需要 `dataZoom` 与大数据量降采样 |
| HTTP | 原生 `fetch` 封装 | 见 §2.2 |
| 单元测试 | Vitest | 与 Vite 同源，无需第二套配置 |
| 端到端 | Playwright | 只覆盖关键路径（登录、环境切换、日志查询） |
| 包管理 | pnpm | 严格依赖树，避免幽灵依赖 |
| 代码检查 | ESLint + Prettier | 见 `开发规范.md` §5 |

### 2.1 为什么是 Vue 而不是 React

这是本项目里**唯一**一次"选生态"而非"选能力"的决策，理由必须写清楚，
否则后人只会看到结论。

- **决策面更小。** React 的核心只有视图层，路由、状态、表单、请求都要各自选型，
  每个选型都会随时间漂移。Vue 的 Router 与 Pinia 是官方配套，
  管理后台所需的决策从"六七个"降到"两三个"。
  对"人类指挥、agent 落地"的协作模式，**决策点少 = 漂移少**。
- **模板语法比 JSX 更受限。** 受限在这里是优点：模板的表达能力窄，
  agent 生成的代码形态收敛；JSX 里同一件事有太多种写法，
  在一个会长期由 agent 追加页面的工程里，写法收敛比表达力更重要。
- **代价（如实记录）**：Vue 的公开语料少于 React，agent 遇到冷门问题时
  一次写对的概率略低；遇到复杂泛型推导时错误信息也更差。
  缓解方式与 C++ 侧一致：**先把接口契约与类型固定，再让 agent 填实现**。

**不用 Nuxt**：管理后台是内网/后台应用，不需要 SSR 与 SEO，
引入服务端渲染只会多一个必须常驻的 Node 进程，与"原生部署、少常驻进程"的原则冲突。

### 2.2 为什么不用 axios

`fetch` 已经够用，而管理端只需要四件事：加统一响应包解包、附加 Cookie、
把非 2xx 转成带错误码的异常、支持取消。这四件事在 `src/api/client.ts` 里约一百行。
引一个请求库意味着多一份依赖与一条供应链风险，收益不足。

**不用 GraphQL / 不用 ORM 类客户端**：服务端是 REST，前端再加一层查询语言
只会让两端说法不一致。

### 2.3 为什么图表不用 Vico 或 ECharts 以外的东西

Android 端用 Vico（Compose 原生）。Web 端无法复用，也不需要复用——
两端渲染的是**同一份服务端数据**，不是同一份渲染代码。
ECharts 在时序场景的成熟度（缩放、降采样、大点数渲染）高于其他候选。

## 三、工程结构

```
admin-web/
├── package.json / pnpm-lock.yaml
├── vite.config.ts / tsconfig.json / index.html
├── .env.development / .env.production
├── src/
│   ├── main.ts              应用入口
│   ├── App.vue              根组件（仅承载路由出口与环境横幅）
│   ├── api/                 唯一与服务器通信的层
│   │   ├── client.ts        fetch 封装：响应包解包、Cookie、错误码
│   │   ├── types.ts         与服务端契约一一对应的类型
│   │   ├── auth.ts / devices.ts / users.ts
│   │   └── sensors.ts / logs.ts / ota.ts / analytics.ts
│   ├── stores/              Pinia
│   │   ├── session.ts       当前用户与能力
│   │   ├── environment.ts   当前环境（demo / prod）
│   │   └── devices.ts       设备列表与当前选择
│   ├── router/index.ts      路由表 + 权限守卫
│   ├── permissions.ts       权限矩阵（**数据，不是散落的 if**）
│   ├── views/               一页一个文件，与 管-F## 对应
│   ├── components/          环境横幅、权限门、空态、错误态
│   └── styles/
└── tests/                   Vitest 单元；Playwright 在 e2e/
```

规则：

1. **只有 `src/api/` 允许出现 URL 与请求逻辑。** 组件与 store 不直接 `fetch`。
   这保证接口变更只有一个落点。
2. **只有 `src/permissions.ts` 允许出现角色判断。** 见 §五。
3. **`views/` 与 `管-F##` 一一对应**，文件名即需求编号的中文页名，
   便于按功能追溯矩阵排期（与 `README.md` §5.2 同一原则）。

## 四、认证与安全

### 4.1 会话票据的传输方式（对服务端的明确要求）

现有文档只说"会话票据"，未说如何携带。管理端**要求**：

| 项 | 要求 |
| --- | --- |
| 载体 | **HttpOnly + Secure + SameSite=Strict 的 Cookie** |
| 不使用 | `localStorage` / `sessionStorage` / 可由脚本读取的任何位置 |
| 原因 | 管理端要展示日志与用户输入的自由文本；票据放在脚本可读处，一次 XSS 就等于票据泄露 |
| 同源 | 前端与 API **同源部署**（nginx 同域），因此无需 CORS，也不放宽 SameSite |

**这是对服务器端的接口要求，需要落到 `服务器端程序架构.md` §4.3 与协议规范 §7.6。**
在服务端支持之前，登录页无法闭环——这一点在 §六的依赖里单列。

### 4.2 CSRF

Cookie 方案带来的固有面。防护为两层，缺一不可：

1. `SameSite=Strict`：跨站请求不携带 Cookie。
2. 双提交令牌：服务端下发一个可读的 `csrf_token`，前端在
   **所有非幂等方法**（POST/PUT/DELETE/PATCH）上回填 `X-CSRF-Token` 头，
   服务端比对。

仅靠 `SameSite` 不够：它依赖浏览器行为，且不覆盖同站子域场景。

### 4.3 前端权限只是体验，不是边界

`前端程序架构.md` §四已确立此原则，管理端沿用并强化：
所有受限操作仍由服务端校验（§4.4 权限矩阵）。前端隐藏按钮只为了避免误操作，
不能作为安全依据——**任何人可以绕过前端直接调 API**。

### 4.4 XSS 面

- 日志、错误信息、用户名一律按文本渲染，**禁止 `v-html`**。
- 日志内容可能包含设备上报的任意字节，是天然的注入载体。
  Vue 的默认插值已经转义，需要防的是"为了高亮而引入 `v-html`"这种自作聪明。
- 不使用 `eval` / `new Function`。

### 4.5 不使用明文

`nginx` 只提供 HTTPS，管理端不提供"跳过证书校验"的开发开关——
这类开关一旦存在，就会在某次现场调试里被带进生产。

## 五、权限模型

`src/permissions.ts` 把服务端 §4.4 的矩阵**原样**表达为数据：

```ts
// 与服务端 permission.hpp 的矩阵一一对应。改动必须两端同步。
export const CAPABILITIES = {
  view_device:   ['superadmin', 'admin', 'operator', 'viewer'],
  send_command:  ['superadmin', 'admin', 'operator'],
  // ...
} as const
```

两条硬约束：

1. **矩阵是数据。** 页面通过 `can('view_device')` 询问，不写 `role === 'admin' || ...`。
   散落的 `if` 会在第一个人改了服务端矩阵时悄悄失真。
2. **服务端矩阵是权威。** 前端这份的用途是隐藏入口；
   若两者不一致，以服务端为准，前端差异按缺陷修。

## 六、环境（demo / prod）

`服务器端程序架构.md` §2.1 有 `environments` 表，`devices.env_id` 是必须的，
理由是"演示与生产必须隔离，否则演示数据会污染生产、生产固件会被推到演示机"。

管理端据此设计：

| 项 | 设计 |
| --- | --- |
| 当前环境 | 存在 `stores/environment.ts`，**不持久化到 localStorage**，刷新后重新选择 |
| 可见性 | 常驻彩色横幅（生产环境为醒目色），任何页面都不例外 |
| 切换权限 | 仅 `superadmin`（见 §4.4 矩阵"跨环境切换"一行） |
| 数据范围 | 所有列表与图表**按当前环境过滤**，不存在"默认全部环境"的视图 |
| 危险操作 | 固件下发、配置修改前，二次确认框必须显示目标环境名 |

**刷新后不保持环境选择**是刻意的：一个能跨刷新存活的"当前环境"，
最容易在操作员以为还在演示环境时把固件推到生产。
重新选择是一次廉价但有效的停顿。

## 七、B10 与 B11：接口预留，语义未定

用户明确指示：**工时统计与分类（B10）与跨环境总览与演示数据（B11）
需要工程后期才能确定具体形态。**

因此本设计对这两项**只做预留，不做实现，也不做猜测**：

| 项 | 处理 |
| --- | --- |
| 路由 | 占位页存在，页面内明示"口径待定"，不渲染任何臆造的曲线或统计 |
| 接口 | 保留 `api/analytics.ts` 中的 `getWorkHours()` / `getCrossEnvironmentOverview()` 两个签名，返回类型标注 `TODO: 口径待定` |
| 不做 | 不建表、不定字段、不写聚合 SQL、不在页面硬编码分类枚举 |

**为什么不先做一版"大概的"**：`服务器端程序架构.md` §4.9 已经写明
"工时统计当前仅为提案"，其分类来源（climb/inspect/idle/maintenance）尚未确认，
且表结构缺少操作员维度。先实现一版会产出**看起来能用但口径错误**的统计，
而错误口径的数据比没有数据更危险——它会被人引用、写进报告。

B10 一旦定口径，落点是：服务端加 `user_id` 维度与聚合（§4.9 已给出方向），
前端把占位页替换为真实图表，路由与菜单不需要改动。

## 八、部署

管理端**不引入 Node 运行时**。构建产物是静态文件，由既有的 nginx 提供：

```
/opt/km3-web/
├── releases/<version>/        # 版本化目录，与设备端/服务端同一约定
└── current -> releases/<version>
```

nginx 配置要点：

| 项 | 值 | 理由 |
| --- | --- | --- |
| 静态根 | `/opt/km3-web/current` | 与 `/api/v1` 同域，Cookie 才能同源 |
| SPA 回退 | `try_files $uri $uri/ /index.html` | 前端路由的前进/刷新不 404 |
| 缓存 | 带 hash 的资源长缓存；`index.html` **不缓存** | 否则发版后用户拿到旧入口引用新资源 |
| API 反代 | `/api/` → 本机 `km3-server` | 同源，避免 CORS |

**发布流程**与设备端一致：构建 → 上传到 `releases/<version>/` →
切换 `current` 符号链接 → 校验 `index.html` 可访问。
静态站点的回滚就是切回上一个目录，无需停机。

## 九、CI

新增 `web` job（见 `.github/workflows/ci.yml`）：

```
pnpm install --frozen-lockfile
pnpm run typecheck      # vue-tsc --noEmit
pnpm run lint
pnpm run test:unit      # Vitest
pnpm run build          # 产物必须能构建出来
```

`pnpm run build` 是必要的：类型检查通过不代表构建通过
（`.vue` 单文件组件的模板编译有自己的错误面）。
