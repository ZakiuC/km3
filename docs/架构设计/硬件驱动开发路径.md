# 硬件驱动开发路径

本文把「厂家手册到手 → 上机只读探测」这一段固定成 **12 步编号路径**。
每一步只给**命令**与**完成判据**，不给散文。步骤编号是**交付顺序**，也是硬停的坐标。

适用范围：CAN / CANopen 设备。换总线（RS485、USB-CAN）时步骤结构不变，
只换第 3 步的 `--bus` 取值与第 7 步的标准层实现。

## 前置：命名与总线归属（唯一权威）

`CAN-x` 指**主板 CAN 的第 x 个口**，因此数字与内核接口名**差一位**：

| 逻辑名（配置/工具/驱动统一使用） | 内核接口 | 硬件含义 | 协议 | 第 3 步的 `--bus` |
| --- | --- | --- | --- | --- |
| `can-1` | `can0` | 主板 CAN 第 1 口 | CAN 2.0B | `can-1` |
| `can-2` | `can1` | 主板 CAN 第 2 口 | CAN 2.0B | `can-2` |
| `usb-can-1` | `can2` | **USB 转 CAN 模块** | CANfd | `usb-can-1` |

> 陷阱：内核里的 `can2` 是 USB 转 CAN 模块，**不是**清单里的 CAN-2。
> 写错下标的表现是「电机不动」，是最难反查的一类故障。
> 完整映射表与实测记录见 `docs/架构设计/设备端程序架构.md` §2.1.3。

工具、驱动、配置一律用**逻辑名**；内核接口名只在最底层映射表里出现一次。

已实测的边界（直接采用，不要再假设）：

| 事实 | 后果 |
| --- | --- |
| `can0`/`can1` 均 UP，**can0=500k / can1=1M**，驱动 mcp251x（SPI） | 速率是部署参数，不写死 |
| 主板 **不支持 CAN FD** | CANfd 设备必须走 USB 转 CAN，接口显式暴露 `SupportsFd()` |
| `vcan` 不可用（内核未开 `CONFIG_CAN_VCAN`） | 无对端时的回归路径是**控制器硬件回环** |
| CAN 专有错误计数**不在 sysfs** | 总线健康度**必须走 netlink** 的 `IFLA_INFO_XSTATS` |
| km3 用户 uid=999、`CapEff=0` | 能开 `AF_CAN`/`SOCK_RAW` 绑 `can1`；`ip link set` 报 Operation not permitted |
| 根分区仅剩约 4.1 GiB | 日志/模型/录像不得写根分区 |

## 硬停规则（越过即事故）

1. **手册未到时，agent 不得越过第 4 步去填任何厂家索引与标度。**
   对象字典索引、控制字/状态字位定义、工作模式码、位置与速度标度 —— 一条都不许猜。
2. **未核对的 `od.json` 条目一律 `unverified`**，且运动路径被
   `#if !MODEL_OD_VERIFIED` 加 `#error` 挡在编译期。未核对的对象字典
   **不可能**编译出一个会动的二进制。
3. 「CiA 402 惯例是 0x6040，先填上」不是进度：它把故障从编译期搬到现场，
   而现场的表现是电机按错误的方向或错误的距离动。惯例是**线索**，不是**来源**。
4. 手册缺项写进 `docs/硬件手册/<型号>/README.md` 的未确认项表；
   代码里的占位值必须带 `// 待手册确认` 且**不得**被第 6 步之外的测试绕过。
5. 「手册外的信息」（只能从厂家上位机软件看到的参数）单独标注来源，
   不与手册来源混用 —— 见 `docs/硬件手册/_模板/README.md` 末节。

## 1. 手册投放

```sh
# 目录名用型号，不用中文别名（别名是我们起的，会在不同文档里漂移）
mkdir -p docs/硬件手册/<型号>/协议
cp docs/硬件手册/_模板/README.md               docs/硬件手册/<型号>/README.md
cp docs/硬件手册/PMP4010/协议/README.md        docs/硬件手册/<型号>/协议/README.md
# 手册与协议文件按建议名放好（对象字典.md / 控制字与状态字.md / PDO映射.md / EMCY错误码.md）
# EDS/DCF 原样放入，不编辑、不重排、不格式化
```

**完成判据**

- `docs/硬件手册/README.md` 的目录约定被遵守：目录名是**型号**，不是别名。
- 该硬件 README 的「已有资料」表登记完毕，表头为 `文件 | 说明 | 状态`；
  状态只能取 `已收` / `待提供` / `手册外`，不给裸空白。
- 「要厂家解答的问题」按 A（对象字典）/ B（PDO 映射）/ C（EDS/DCF）/ D（操作手册）
  四组填好，每行写清**为什么阻塞**。
- 「反馈能力」一节选定 `none` / `readback` / `cyclic` 之一 —— 它决定第 9 步的界面
  能不能显示「当前状态」，不许留「待确认」到第 9 步。
- EDS/DCF 保持原样（改动会让厂家工具的校验失效）。
- **未把手册内容复制进 `docs/架构设计/`**：设计文档只写「依据某手册的某节」。

## 2. 资料索引：消解未确认项四组

```sh
grep -n "^### [A-D]\." docs/硬件手册/<型号>/README.md
grep -n "待确认\|待提供" docs/硬件手册/<型号>/README.md
```

**完成判据**

- A / B / C / D 四组的**每一行**都落到两种终态之一：
  `已消解（依据 <文件> §<节/页码>）` 或 `保持未确认（缺 <文件>）`。
- `PMP4010` 的四组未确认项（A 对象字典、B PDO 映射、C EDS、D 操作手册）
  按同一条规则处理；同一条事实只能有一个终态。
- E 组（属设计或实测，不属手册）**不改 `docs/架构设计/`**：
  先报告差异，由人类决定改文档还是改实现。
- 消解后仍为「待确认」的行必须能指出**缺哪份文件**，不能只是留着。

## 3. 生成骨架

```sh
bash tools/hwdriver/new-driver.sh <型号> --bus can-2                     # 默认 dry-run，只打印
bash tools/hwdriver/new-driver.sh <型号> --bus can-2 --count 4           # 该型号几台
bash tools/hwdriver/new-driver.sh <型号> --bus can-2 --count 4 --apply   # 真正落盘
```

**完成判据**

- `--bus` 取逻辑名（`can-1` / `can-2` / `usb-can-1`），脚本负责映射到内核接口，
  生成物里**不出现内核接口名**，只出现逻辑名。
- dry-run 输出中列出的每个路径都是将要新建的，**不含**对既有文件的修改。
- 生成物落在 `device/drivers/<型号>/` 下并带 README；结构以 `device/drivers/_template/` 为准：
  根下 README.md、CONTRACT.md、CMakeLists.txt；driver/ 下 driver.hpp、driver.cpp、od.json；
  tests/ 下 test_driver.cpp 与 CMakeLists.txt；tools/ 空目录用于第 8 步。
- 三处落点都到位：`device/drivers/<型号>/`（骨架）、`device/CMakeLists.txt`
  （在「硬件驱动」标记区追加一行 `add_subdirectory`）、
  **`device/config/canopen_nodes.json`**（追加节点块）。
- 节点号分配方式**未由手册确认**时，节点表的 `enabled` 必须是 `false` ——
  这是**唯一**的节点号来源，驱动与工具都读它，不得在代码里另写 `node_id` 常量
  （`node_id = 1` 是纯占位，不是默认值）。
- `git status --short` 只有新增（`??`），`device/CMakeLists.txt` 与
  `device/config/canopen_nodes.json` 出现 ` M` 是**预期**（生成器追加，不是覆盖）。
- 契约文件里的 **RT 可达性表**逐函数填好。未核对状态下的正确结论是
  「本驱动没有任何函数可进实时线程」——那是结论，不是待办。
- **反馈能力只在手册目录的自述文件里声明一次**（第 1 步），
  驱动的自述文件与契约文件可以引用，**不得复制结论**；写两处就是两份真相。
- 取 `--bus usb-can-1` 时，生成物必须显式声明 CAN FD 能力
  （与 `device/include/km3/hal/can_device.hpp` 的 `CanCapabilities` 对齐）。
- 取 `--bus can-1` / `can-2` 时声明**不支持** CAN FD：主板仅 CAN 2.0B。

## 4. 填 `od.json`（硬停步骤）

```sh
# 只填已核对的厂家事实，每条带 status 与 cite
$EDITOR device/drivers/<型号>/driver/od.json
# 1) 每个条目都必须同时有 status 与 cite 两个键（含 device 段与 entries 段）
jq -e '.. | objects | select(has("status")) | has("cite")' \
   device/drivers/<型号>/driver/od.json
# 2) status 只能是三个值之一（有输出即非法）
jq -r '.. | objects | select(has("status")) | .status
       | select(. != "unverified" and . != "assumed" and . != "verified")' \
   device/drivers/<型号>/driver/od.json
# 3) verified 必须有非空 cite；unverified 必须 cite 为 null
jq -r '.. | objects | select(.status == "verified")
       | select(.cite == null or .cite == "") | "\(.key) 缺 cite"' \
   device/drivers/<型号>/driver/od.json
jq -r '.. | objects | select(.status == "unverified") | select(.cite != null)
       | "\(.key) unverified 却带 cite"' \
   device/drivers/<型号>/driver/od.json
```

**完成判据**

- 每个条目都有 `status` 与 `cite` 两个字段，无例外。`status` 取三值，
  与 `device/drivers/_template/driver/od.json` 的既有约定一致
  （模板 `_comment` 只写了 `unverified` / `verified` 两值，第三值 `assumed` 由本文补：
  它让「有人口头说过」与「手册写了」在代码里可区分，因此必须与另外两值并列，不能合并）：

  | 值 | 含义 | 能否进生成物 |
  | --- | --- | --- |
  | `unverified` | 无依据 | 否 |
  | `assumed` | 有人给了口头依据，仍需书面确认 | 否 |
  | `verified` | 有可解析的 `cite` | 是 |

  `assumed` 不是 `verified` 的弱化版，是**另一类状态**：它让「口头说过」与
  「手册写了」在代码里可区分。把 `assumed` 当 `verified` 用等于删除这条区分。
- `verified` 条目的 `cite` 必须指向 `docs/硬件手册/<型号>/` 下**真实存在**的文件，
  并带章节或页码；指向惯例（「CiA 402」）不算 cite。
- **`unverified` 的 `cite` 必须是 `null`**：`unverified` 又带 cite 是自相矛盾，
  说明有人把来源抄进了没核对的条目里。CI 由第 11 步的溯源检查拦下。
- 模板里 `od.json` 的 `_comment` 说明的是**字段语义**，新驱动的自述文件说明的是
  **本型号当前缺什么**；两者不重复。生成器的输出提示里若出现旧字段名
  （例如 `source` / `verified`），以 `od.json` 的实际字段为准并**报差异**，
  不要按提示去改 `od.json`。
- 手册未到时，全部条目保持 `unverified`，**本步骤到此为止**，不得进入第 5 步去生成常量。
- 手册到了但只覆盖一部分时，只把**被覆盖的那几条**改成 `verified`，
  其余保持 `unverified` —— 条目粒度的诚实，不是文件粒度的诚实。

## 5. 生成常量

```sh
python3 tools/hwdriver/gen-od.py --model <型号>              # 读 od.json，写两个生成物
python3 tools/hwdriver/gen-od.py --model <型号> --check      # 漂移检查：不写文件，不一致退出 1
# CI：对每个已落地的驱动跑一次 --check（--check 必须带 --model，不会自己扫全仓库）
for m in $(ls device/drivers | grep -v '^_'); do
  python3 tools/hwdriver/gen-od.py --model "$m" --check || exit 1
done
```

**完成判据**

- 产出 `od_generated.hpp` 与 `tools/hwtui/canopen_consts.py`，两者头部带
  `DO NOT EDIT` 与 `od.json` 的 sha256。
- `--check` 退出码 0；改 `od.json` 而不重新生成 → `--check` **非零**退出
  （这就是漂移 diff 的定义）。`--check` **必须带 `--model`**：它只比对单个驱动，
  不扫全仓库，所以 CI 里要自己循环（见上方命令）。
- 模板目录用 `--allow-placeholder`；**对真实驱动不得使用该开关**，
  它会放过占位型号，等于关掉「未核对就编不过」这道闸。
- 生成器只输出 `verified` 条目为可用常量；`unverified` 条目要么不出现，
  要么以 `kUnverified...` 前缀出现并带注释。
- **CI 必须包含** `gen-od.py --check` 这一步，与 `tools/check-docs.sh` 同级。
- 生成物与驱动的接线是**分两步**的：`od_generated.hpp` 先就位，但
  `driver.hpp` 在 `kOdVerified` 为 false 时**不得** include 它（全占位生成物 include 进来
  只会让整条构建阶梯失败）。因此「守卫已就位、生成物未接线」是手册到手前的**正确状态**，
  不是待办 —— 接线发生在第 4 步有一次 `verified` 之后。

## 6. 契约测试

```sh
cmake -S device -B build-host -DCMAKE_BUILD_TYPE=Debug
cmake --build build-host -j"$(nproc)"
ctest --test-dir build-host --output-on-failure
ctest --test-dir build-host -R <代号> --output-on-failure   # 只看本驱动
```

**完成判据**

- 测试放在 `device/drivers/<型号>/tests/` 下（**不是** `device/tests/` ——
  那里是设备端骨架的测试，驱动测试跟驱动走），复用 `device/tests/test_harness.hpp`
  （零依赖骨架）与 `device/include/km3/hal/mock_devices.hpp` 的 `MockCanDevice`；
  链接用 `device/drivers/<型号>/tests/CMakeLists.txt` 的 `target_link_libraries`。
- **断言语义，不断言字节序列**：断「使能后 `Statusword` 的 Ready 位为 1」，
  不断「发出了 0x0006」—— 后者一改位定义就假红，且掩盖真实语义。
- **`kOdVerified` 为 false 时，断言零字节发出**：
  调用任何会到达总线的运动 API 后，`MockCanDevice::SentFrames()` 为空。
  能到达总线的运动路径由 `#if !MODEL_OD_VERIFIED` + `#error` 挡在编译期，
  因此「编译不过」本身也要有一条测试或 CI 步骤去证明它确实挡得住。
- 测试在 `build-host` 与 `build-tsan` 两个构建目录下都通过
  （`-DKM3_SANITIZER=thread`，见 `docs/架构设计/开发规范.md` §3.3）。

## 7. 标准层归位：CANopen

```sh
grep -rn "0x6040\|0x603F\|0x1018" device/drivers/ tools/ | grep -v canopen.py
```

**完成判据**

- CANopen 的帧组装、SDO 上传/下载、PDO 打包、心跳与 NMT 状态机只属于标准层；型号驱动不得重复实现。
  Python 入口是 `tools/hwtui/canopen.py`，C++ 非实时有界 SDO/NMT 入口是 `device/include/km3/canopen.hpp`（`km3_canopen`）。已就位的入口点（直接复用，
  不要另起一套）：`SdoClient`（读）/ `scan_nodes()`（识别节点）/ `HeartbeatMonitor`
  与 `NmtMaster` / `parse_emcy()` / `read_pdo_mapping()` 与 `read_pdo_communication()`
  （第 12 步要读的正是这几项）。第 5 步的 `canopen_consts.py` 由生成器产出到同一目录。
- 上一条命令的命中只允许出现在标准层与 `od.json`；驱动通过生成 OD 的 key/index 元数据调用标准层，**驱动里重复实现帧协议即失败**。
- 标准层不 import 任何具体型号模块（反向依赖会毁掉第 10 步的解耦断言）。
- 驱动的自述文件声明「标准层职责 / 本驱动职责」的分界。
- C++/Python 的 wire/state 定义唯一来源为 `tools/hwtui/canopen_wire.json`，由
  `tools/hwdriver/gen-canopen.py` 生成各语言定义，`--check` 验证漂移。事务执行器分别实现，
  用同一份 `tools/hwtui/vectors/canopen_golden.json` 完整对话重放验收；不以共享常量冒充共享算法。
  这修正了旧版“Python必须是C++唯一实现来源/互为生成物”的过度约束：Python执行器依赖动态对象，
  C++边界要求有界且无动态分配，当前不嵌入Python或宣称已具备跨语言算法生成器。
  C++当前仅覆盖有界SDO/NMT与状态判定；PDO/心跳的C++执行器未实现，不自动宣称整个标准栈就绪。

## 8. 驱动自带工具

```sh
python3 device/drivers/<型号>/tools/<型号>.py --help
python3 device/drivers/<型号>/tools/<型号>.py --init --bus can-2
python3 device/drivers/<型号>/tools/<型号>.py --test --bus can-2
```

**完成判据**

- `--init` 与 `--test` 是**一级子命令**：`--help` 顶层就能看到，不需要翻二级。
- `--init` 只做只读识别与参数落盘；`--test` 在无对端节点时走
  控制器回环路径（见 `docs/架构设计/实测基线.md` §9.3）。
- **工具永不自己执行 `ip link set`**：只读 `/etc/km3/device.json`、
  `ip -details link show`，写 `km3` 拥有的 `/etc/km3/can.env`，最后打印 root 命令（见下节）。
- 工具不依赖板上自编译：走板端 `python3` 3.10.12 与既有 can-utils，
  **不新增 aarch64 二进制**（这是本路径不改 deploy 脚本的前提）。

## 9. TUI 面板

```sh
# 面板外壳：无终端尺寸时的最小验证（--once 只画一帧，不进 curses）
python3 tools/hwtui/tui.py --rows 24 --cols 80 --once
```

**完成判据**

- 复用 `tools/hwtui/tui.py` 的纯函数 `render(prev_grid, next_grid)`
  （增量重绘，输入输出都是行字符串，与 curses 无关，因此可单测）
  与 `resolve_size()`（尺寸不可知时的降级入口），加上 `tools/hwtui/discover.py`。
  **新硬件不新增包装脚本**：面板是数据驱动的，不是每型号一份。
- 本步骤只交付**数据**（面板要显示的字段与来源），不改 TUI 外壳；
  新增总线/型号时 `discover.py` 发现它、`render()` 画它，外壳不动。
- 上机验证见第 12 步：`--rows 24 --cols 80` 走的就是 `resolve_size()` 的降级分支，
  正是为「`stty size` 返回 0 0」准备的；面板必须能在没有尺寸的前提下画出一帧。
- `stty size` 返回 `0 0` 时首屏不崩（尺寸不可知必须按默认值渲染）——
  这是板端 SSH 会话的实测行为。
- 面板读的是手册目录自述文件里声明**一次**的反馈能力（`none` / `readback` / `cyclic`），
  不自己判断、也不接受驱动的第二份声明。
- 反馈能力为 `none` 的硬件，面板**不得**维护「当前状态」的权威副本，须显式标注无反馈。
- 面板显示总线健康度时，数据来自 netlink 的 `IFLA_INFO_XSTATS`，不读 sysfs。

## 10. 解耦检查

```sh
bash tools/check-drivers.sh
```

**四条断言**（全部必须过）

1. 每个 `device/drivers/<型号>/` 都有自己的自述文件，且声明归属总线的逻辑名。
2. 驱动之间零耦合：任一驱动不 include 另一驱动的头文件。
3. CANopen 常量与状态机不在驱动内重复实现（标准层唯一）。
4. **反向构建完整性**：删掉或移走任一驱动目录后，
   `cmake -S device -B build-host` 仍配置成功 —— 驱动是可选的，
   不得让设备端骨架对它硬依赖。

**完成判据**

- 四条断言全过；退出码 0。
- 检查器区分「悬空引用」（缺陷）与「尚未实现的占位」（预期）两类输出，
  只把前者计为失败。

## 11. 溯源检查

```sh
bash tools/check-manual-citations.sh
```

**完成判据**

- 每个**索引常量**（对象字典索引、子索引）与每个**标度常量**（每计数单位对应多少
  脉冲 / mrad / rpm、零位偏置）都**在同一行**带可解析引用：文件 + 章节或页码。
- 引用必须解析到 `docs/硬件手册/<型号>/` 下真实存在的文件。
- 缺引用即失败，**不接受「文件头一句全局注释」**：那会让新增常量天然免检。
- 检查器与第 5 步的生成器对「引用格式」用同一套解析规则，不得两处实现。

## 12. 上机：只读探测（can1）

```sh
ssh root@192.168.0.188                      # 空密码；正式部署须改密钥并弃用 root
ip -details -statistics link show can1      # 位速率、状态、netlink 错误计数
python3 device/drivers/<型号>/tools/<型号>.py --init --bus can-2 --read-only
candump -t d can1                           # 旁路观察心跳，不改总线状态
python3 device/drivers/<型号>/tools/<型号>.py --bus-stats --bus can-2
```

**探测内容与完成判据**

- **识别节点**：扫出 `can1` 上应答的节点号，与手册声明的节点号分配方式核对。
- **心跳**：`0x1017` 周期与实际心跳间隔一致（这是断线检测的输入）。
- **SDO 读四项**：`0x1000`（设备类型）、`0x1008`（设备名）、`0x100A`（软件版本）、
  `0x1018`（身份对象）。读到值即证明通讯层通，读不到即证明通讯层不通 ——
  两者都能定位，不要把失败推测成「电机没使能」。
- **`--bus-stats`** 必须打印 `bus-off` / `error-warn` / `arbit-lost` 三个计数。
  **缺终端电阻时这是唯一的可诊断信号**：错误计数增长而没有任何应用层报错，
  是物理层的症状，不是软件的。
- 全程**零运动帧**：不发送 NMT Start、不发送 PDO、不做运动相关 SDO 写。
  只读探测本身会发送 SDO **上传请求**，这是允许的；不允许的是任何写。
- `can1` 保持 `ERROR-ACTIVE`。它是「控制器就绪、总线上还没有对端应答」的正常态，
  不是故障 —— 现场排障时最容易被误判的一条。

## 权限三段式（改 can1 位速率时）

`km3` 用户能绑 SocketCAN、能读写自己的配置，但 `ip link set` 报
Operation not permitted（`CapEff=0`），`systemctl restart km3-can` 报
Interactive authentication required（无 polkit 规则）。因此路径固定为三段：

| 段 | 动作 | 依据 |
| --- | --- | --- |
| 1. 读 | 读 `/etc/km3/device.json` 与 `ip -details link show can1`，确认目标接口、当前速率与容错范围 | 读不需要任何特权 |
| 2. 写 | 写 `km3` 拥有的 `/etc/km3/can.env`（0640 `km3:km3`，km3 可写） | `device/deploy/systemd/km3-can.service` 用 `EnvironmentFile=` 读它，且**放在默认值之后**才能生效 |
| 3. 打印 | 打印需要 root 执行的确切命令，由人类执行 | 工具**永不**自己 `ip link set` |

- **不引入 sudoers，不引入 polkit 提权。** 提权面一开，第 12 步的「只读探测」
  就再也无法被证明是只读的。
- 第 2 段写 `can.env` 之后必须能被第 3 段验证：重新读回文件并打印生效值，
  而不是打印「已写入」。

## 什么时候必须去修 deploy 脚本

**本路径交付的是 Python 源码，不新增 aarch64 二进制。** 因此下列硬编码枚举
**继续有效且不被触碰**（行号是对当前文件的锚点，改了就按新锚点重新对齐）：

| 文件 | 行 | 内容 |
| --- | --- | --- |
| `tools/deploy_device.sh` | 12 | `SERVICES_CORE=(km3-core km3-video)` |
| `tools/deploy_device.sh` | 53 | `for bin in km3-rt-controller km3-core km3-video; do` |
| `tools/deploy_device.sh` | 80–84 | `scp` 上传的二进制列表 |
| `tools/provision_device.sh` | 95 | `UNITS=(km3-can.service km3-core.service km3-rt-controller.service km3-video.service)` |
| `tools/provision_device.sh` | 237 | `已安装 4 个单元` 的提示文本 |
| `tools/provision_device.sh` | 240 | enable 单元的 `for` 循环 |

理由：这些枚举描述的是**设备端进程与 systemd 单元**，而硬件驱动工具是
主机侧/板端 Python，经 `tools/deploy_hwtools.sh` 投放（不走版本目录与符号链接切换，
也不进 `SERVICES_CORE`）。**只要本路径不新增常驻二进制，就不该动它们。**

**但任何硬件第一次交付常驻 aarch64 二进制时，必须在同一提交内引入
`device/deploy/binaries.txt`**，两个脚本都改成从该文件读：

```
# 每行：<name> <class>
km3-rt-controller  service
km3-core           service
km3-video          service
km3-can-probe      tool
```

- `class` 只能取 `service` 或 `tool`。
- `tools/deploy_device.sh` 与 `tools/provision_device.sh` **都**从这里读，
  且对**缺件显式报错**（缺一个二进制就失败，不静默跳过——
  静默跳过的后果是部署「成功」而服务起不来）。
- 修改这两处时必须同步 `tools/README.md` 的描述（第 5 项机检会比对工具索引）。

## 机检挂点

本路径依赖的机检，全部本地可跑、CI 直接复用：

```sh
bash tools/check-docs.sh                  # 文档引用、仓库内路径、目录树、CAN 写法歧义
bash tools/check-drivers.sh               # 第 10 步的四条断言
bash tools/check-manual-citations.sh      # 第 11 步的溯源
python3 tools/hwdriver/gen-od.py --model <型号> --check   # 第 5 步的漂移 diff（逐个驱动）
```

本文放在 `docs/架构设计/` 是刻意的：`tools/check-docs.sh` 第 3 项会校验文档里
反引号引用的仓库内路径真实存在，因此**文档与工具不可能各说各话**。
新增步骤时若引用了还没写的文件，检查器会红——那是正确的反馈。

**红的时候怎么读**，三种命中含义不同，处置也不同：

| 命中 | 含义 | 处置 |
| --- | --- | --- |
| 工具尚未写出（如第 10、11 项的检查器） | 步骤已定案、实现未落地 | **保留引用**，等实现补上；删引用等于删步骤 |
| 手册占位路径（第 1 步写的 `docs/硬件手册/<型号>/README.md`） | 检查器的**存在性豁免只认「文档本身在手册目录下」**，架构文档里引的手册路径不豁免，因此带 `<型号>` 的引用会被当成字面路径报悬空——**这是假报** | 无需处理；不要在本文里为它换写法，同一占位写法在第 1 步出现多次 |
| 设备端骨架目录树 / `tools/README.md` 索引报红 | 与本文无关的既有检查项（第 2、5 项） | 不要顺手改，先确认是谁引入的 |

**写作纪律**（实测踩过，值得记住）：驱动目录里的文件名**不要写成裸的反引号文件名**。
第 1 项对 markdown 引用的解析顺序是「文档同级 → `docs/` → 仓库根」，驱动目录里的
自述与契约文件不在这三处中的任何一处，于是被报成悬空。要引用就写完整仓库路径。
