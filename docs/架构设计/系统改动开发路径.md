# 系统改动开发路径

**这是什么**：`docs/架构设计/硬件驱动开发路径.md` 管的是**新增一个硬件型号**。
本文管**其余四类系统改动** —— HAL 后端、协议层能力、配置 schema、现场取证。

**为什么需要第二份**：只有一份路径时，**第二种活没有归属**，于是每次都靠人临场手写任务书。
手写的那一份无法复用、无法机检、无法积累，而且撰写者往往是团队里最贵的一环。
本文的目的就是把这四类从"临场发挥"变成"照单执行"。

---

## 一、什么时候该走本文，而不是驱动路径

| 改动形状 | 走哪条路 | 判据 |
| --- | --- | --- |
| 新增一个硬件型号（新电机、新传感器） | [硬件驱动开发路径](硬件驱动开发路径.md) | 需要 `device/drivers/<型号>/` 一个新目录 |
| **新增/修改 HAL 后端** | **本文 §三** | 动 `device/src/hal/`、`device/include/km3/hal/` |
| **新增协议层能力**（PDO、心跳、失联、新报文） | **本文 §四** | 动 `device/src/canopen/`、`device/include/km3/canopen*.hpp` |
| **改配置 schema** | **本文 §五** | 动 `device/include/km3/config.hpp`、`device/src/common/config.cpp`、`device/config/device.json` |
| **现场取证**（读回、计数实验） | **本文 §六** | 目的是"弄明白现状"，不是"改代码" |

**四类共有的特征**：**改动横跨多个既有模块**，没有新目录可生成，因此 `new-driver.sh`
那一套生成骨架的机制完全不适用——这正是它们落回人手的原因。

## 二、谁做：分工（**这条优先于一切省事考虑**）

| 角色 | 做什么 |
| --- | --- |
| **人类** | 决策（周期、位速率、是否写电机参数）、现场验证（带载运动、断电试验）、授权不可逆操作 |
| **便宜 agent** | **落地执行**：照任务书写代码、跑测试、跑机检、出报告 |
| **主会话 agent** | **只做三件**：现状侦察与事实核准、写任务书、**独立验收** |

**主会话不得自己动手改业务代码。** 它做侦察和验收是必要的（那需要判断力，而且便宜 agent
会猜——本项目已因猜错付出过代价），但**实现必须派出去**。理由是本文开头那条：目标是让
便宜 agent 长出能力，不是让贵的那个更快。

**主会话可以做**（不属于"动手改业务代码"）：
- 只读侦察：`grep`/`sed`/读文件/上板只读读回
- 写**任务书**（本文 §二 的骨架）
- **独立验收**：重跑闸门与测试、独立复算数字、做对抗性复核
- **文档与台账**：`device/drivers/<型号>/driver/od.json`、
  `device/drivers/<型号>/CONTRACT.md`、`docs/硬件手册/<型号>/README.md`、验收记录
- **小修**：单文件、不动协议语义、不涉发帧（如删掉一个多余的 `setsockopt`）

**一句话判据**：**改动超过 1 个文件，或涉及发帧/电机/协议语义 —— 派出去。**

## 三、HAL 后端类

**实例**：`device/src/hal/socketcan_device.cpp`（2026-10-16 由便宜 agent 完成）。

### 3.1 必须给足的前置事实

派活前，任务书里必须写死这些（否则便宜 agent 会自己猜，而猜错的表现是"看着合理"）：

1. **要实现的接口全文**（路径 + 每个纯虚函数），及**硬件能力**（是否支持 FD、最大位速率）
2. **已知的坑**，逐条列出。例如：
   - `IsDlcValid()` 必须基于**原始** `dlc` 校验，用钳制值会让校验永不触发
   - FD 帧必须**拒绝**，不能静默降级
   - 接口名**只从配置来**，不得硬编码 `can1`
3. **字段名不一致处**（本项目既有且故意）：JSON 里 CAN 端点写 `"iface"`、串口写 `"device"`，
   两者在 `ParseEndpoints` 统一落到 `BusEndpoint::device`（见 `device/src/common/config.cpp`）
4. **RT 纪律**：哪些函数可能被实时线程调用，那些路径禁止分配/IO/日志/阻塞

### 3.2 验收要点

- **帧编解码往返测试**（字节序！本项目在 CAN 解码上犯过三次字节序错误）
- **非法输入被拒**：FD 帧、超长 `dlc`、未配置的接口名
- **超时是正常状态**（`ECommandTimeout`），不是错误
- **上板取证必须用接口计数差分**，不得用 `candump`
  （socket loopback 已在 `device/src/hal/socketcan_device.cpp` 里关闭，本机看不到自己发的帧）

## 四、协议层能力类

**实例**：SYNC 生产者（`device/src/canopen/sync.cpp`，2026-10-16）、PDO 收发（待做）。

### 4.1 必须给足的前置事实

1. **协议语义的出处**：手册哪一页、`od.json` 哪一条。**不得让 agent 去查惯例**——
   惯例是线索不是来源（见[硬件驱动开发路径](硬件驱动开发路径.md) 硬停规则 3）
2. **本机实测现状**：哪些对象存在、哪些中止、当前取值
3. **线程归属**：这类功能**必须让 agent 判断并说明理由**，不接受"实测没阻塞过"
4. **`od.json` 里可能不存在的对象**（如本机 `1006h` 中止 `0x06020000`），
   以及由此推出的结论（周期只能靠主站定时器）
5. **现场陷阱**：例如 `1007h` = 0（同步窗口关闭）意味着 **SYNC 停发不会自动产生 EMCY**

### 4.2 必须让 agent 自己判断的设计问题

任务书里**不要**替它决定，但**必须要求它写明理由**：

- 线程归属（RT 线程 vs 边界线程）
- 报文顺序（如 SYNC 与 RPDO：顺序错了会凭空多一个周期延迟）
- 缺失容忍（如 TPDO 不是每周期都有）

### 4.3 验收要点

- **无分配断言**（RT 路径）
- **顺序测试**（不只测"都发出去了"，要测**先后**）
- **缺失容忍测试**
- **字节序往返**
- 帧长度校验（映射的条目数决定期望长度，发错长度**不报错但静默错位**）

## 五、配置 schema 类

**本项目有"声明了但不生效"的前科**（git log `ef3a36a`：配置加载期三处静默失效）。
因此这类改动的验收只有一条核心：**证明字段真的生效**。

### 5.1 必须给足的前置事实

- 字段放哪个 struct、JSON 里放哪一段（**两者可以不同名**，本项目 CAN 端点就是这样）
- 是否需要被实时线程只读（若是，注意 `ConfigSnapshot` 的平凡可拷贝静态断言）
- 合法范围与越界行为

### 5.2 验收要点（**缺一不可**）

1. **完整链路追踪**：JSON 键 → `config.cpp` 解析 → struct 成员 → 使用点。
   每一步给出 `file:line`，**不能只说"加了字段"**
2. **端到端生效证明**：改配置值 → 跑到使用点 → 行为跟着变
3. **越界被拒**：零、负数、超上限，逐个测
4. **默认值不改变既有启动行为**
5. **模板同步**：`device/config/device.json` 是否要一起改

## 六、现场取证类

**实例**：PDO/SYNC 只读探测（2026-10-16）。

### 6.1 铁律

1. **只读就是只读**：脚本要**自带计数**，证明发出的每一帧都是读请求。
   写法：包装发送层，对每个出帧分类，末尾断言"非读帧 == 0"
2. **绝不采信 `/tmp` 里的既有脚本**。本项目 `/tmp` 长期堆着历史探测脚本，
   来源不明、未审。要么重写，要么先完整读一遍
3. **两种独立实现互证**（本项目在解码上犯过三次字节序错误，
   单一实现 + 只读一次是本项目最贵的两次错误之一的成因）
4. **重复读取**：关键值连读 5 次，确认稳定
5. **中止与超时是两件事**：中止（如 `0x06020000`）证明对象**不存在**；
   超时**不能**证明任何事。分开记录
6. **取证脚本放 `/tmp`**，不占根分区（板端根分区余量小）；用完清理

### 6.2 上板纪律

- 板子：`ssh root@192.168.0.188`（**有线**；`192.168.1.253` 是同一台的 wifi，不是两台机器）
- **根分区余量很小**，不要把日志/脚本/产物写进根分区
- 现场服务（`km3-can` / `km3-rt-controller` / `km3-core`）**不得重启或替换**
- 收工前清理临时文件、核对服务仍 active、核对接口状态

## 七、任务书骨架（复制这一段）

派活时按这个骨架写。**每一节都不可省**——省掉哪节，agent 就在哪节猜。

```markdown
# 给 <agent> 的任务：<一句话目标>（<日期>）

## 任务目标
<要达成什么；明确写出"本任务不做 X">

## 零、必须先读
<路径清单，按顺序。含本文 §一 对应的那条路径>

## 一、已核实的事实（**直接采用，不要重新推导**）
<主会话侦察到的现状。附取证方式与证据强度（实测/手册/厂家口头）>
<⚠ 每条都要标"这是实测"还是"这是手册"还是"这是惯例"——三者可信度不同>

## 二、要做的 N 件事
<按依赖排序，一件一件来>
<每个设计问题写明"必须判断并说明理由"，但不要替它决定>
```

## 八、已知的坑（派活时按需摘进任务书）

| 坑 | 表现 | 出处 |
| --- | --- | --- |
| 工具链路径必须绝对 | 相对路径被解析到构建目录，报 "Could not find toolchain file" | `CLAUDE.md` |
| TSan 必报内存映射错 | `unexpected memory mapping`，**不是代码问题**；`setarch -R` 后才是真结果 | 2026-10-16 |
| `candump` 不能当发帧证据 | loopback 关闭后本机看不到自己发的帧 | `device/src/hal/socketcan_device.cpp` |
| 整数后缀破坏正则 | 生成常量是 `0x1400u`，按 `0x1400` 匹配会漏 | 本项目 |
| 字节序 | 自写解码器三次错，产出"看着合理"的错数 | `docs/硬件手册/PMP4010/板端只读验收-2026-10-16.md` §六 |
| 字段名不一致 | JSON `iface` vs C++ `device`（故意的） | `device/src/common/config.cpp` |
| 配置静默失效 | 声明了但不生效 | git log `ef3a36a` |
| 报数不实 | "全绿"的数字是真的时候，两个闸门仍可能是红的 | git log `2884dd1` |
| 时钟推进用 `sleep_for` | 逐次漂移；必须用绝对单调时钟 | `docs/架构设计/开发规范.md` |
| 写文件读到半截 | 判断文件损坏前，先比对 mtime 与读取时刻 | 本项目 |

## 九、验收者的纪律（主会话自己遵守）

1. **不采信自述**。报告里的"全绿""15/15""8478 条"**一律自己重跑**。
   数字可能是真的，同时掩盖别的问题
2. **独立复算**。合计数自己加一遍（本项目有实例：`2232+5234+921+91 = 8478` 才对得上）
3. **区分"证据"与"声明"**。`candump` 里的帧是声明；接口 TX 计数差分是证据
4. **对抗性复核高危结论**。每个 high 发现都要有独立 agent 尝试推翻
5. **报告要分清三类**：确认成立 / 被推翻 / 无法验证。**不许把"没验"写成"没问题"**
6. **改动能小就小**。验收时发现的缺陷，小修自己做，动语义的退回去重派

## 十、机检挂点

与驱动路径共用同一套（**不新增检查器**——多一套就多一处漂移）：

```sh
bash tools/check-docs.sh                  # 本文引用的仓库路径存在性也由它把关
bash tools/check-drivers.sh
bash tools/check-deps.sh
bash tools/check-manual-citations.sh
```

**本文放在 `docs/架构设计/` 是刻意的**：`tools/check-docs.sh` 第 1 项会校验文档里
反引号引用的仓库内路径真实存在，因此**本文与代码不可能各说各话**。
引用了还不存在的文件时它会红——**那是正确的反馈**，处置办法见
[硬件驱动开发路径](硬件驱动开发路径.md) 的「机检挂点」末节。
