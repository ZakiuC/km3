# 通信协议规范

本文件是三端通信的**唯一权威**。任何接口实现与此处不符即为缺陷。

## 一、协议总览

### 1.1 四条路径

| 路径 | 链路 | 传输 | 序列化 |
| --- | --- | --- | --- |
| A | 上位机 ↔ 设备端（直连） | 自定义 TCP（14 字节头） | Protobuf |
| B | 上位机 ↔ 服务器 ↔ 设备端（中转） | WebSocket over TLS | JSON |
| C | 设备端 ↔ 服务器（直连） | WebSocket over TLS | JSON |
| D | 设备端 ↔ G30 ↔ 服务器（桥接） | 隧道，封装在路径 A 上 | JSON（透传） |

**规则**：只有路径 A 用 Protobuf（高带宽、低延迟、两端都是 C++/Kotlin 可生成代码）。
路径 B/C/D 一律 JSON——便于服务器调试、便于 agent 阅读、便于日志留痕。

### 1.2 时间与序号

| 概念 | 类型 | 用途 |
| --- | --- | --- |
| `ts_us` | `uint64` 微秒 | 二进制帧与数据库内部时间 |
| `ts` | RFC3339 字符串 | 对外 API、JSON 消息、日志显示 |
| `command_id` | UUIDv7 字符串 | 命令全局唯一标识，**由发起方生成** |
| `command_seq` | `uint64` 单调递增 | 防重放（设备侧维护） |

**防重放窗口基于单调时钟，不基于墙上时间**。TL3588 有 RTC 时间回退的实测问题，
墙上时间在启动早期可能旧于真实时间，用它做窗口会让防重放失效。

### 1.3 身份

- 顶层 `Message.id`：本条消息的传输标识（UUIDv4），仅用于请求/响应对应。
- `Command.command_id`：业务命令标识（UUIDv7），跨重连、跨通道保持稳定。
- **两者不得混用**：服务器数据库主键不对外，设备不感知。

## 二、路径 A：上位机 ↔ 设备端（自定义 TCP）

### 2.1 帧格式

```
+--------+--------+--------+--------+------------------+
| Length |  Type  | SeqNum |  CRC   |     Payload      |
| 4 字节 | 2 字节 | 2 字节 | 2 字节 |     N 字节        |
+--------+--------+--------+--------+------------------+
```

- `Length`：整帧长度（含头），网络字节序。
- `Type`：消息类型（§2.2）。
- `SeqNum`：请求/响应配对。
- `CRC`：CRC16-CCITT，校验 Type + SeqNum + Payload。
- `Payload`：Protobuf 序列化。

**这是唯一权威帧定义**。前端实现必须按此解析（用 `protobuf-javalite` 生成代码），
早期前端文档写成「4 字节长度 + JSON」是错的，已修正。

### 2.2 消息类型

```protobuf
enum MessageType {
    HEARTBEAT      = 0x0001;
    COMMAND        = 0x0100;
    COMMAND_ACK    = 0x0101;
    COMMAND_RESULT = 0x0102;
    ESTOP          = 0x0103;   // 紧急停止，独立于 COMMAND
    STATUS_REPORT  = 0x0200;
    SENSOR_DATA    = 0x0300;
    CONFIG_GET     = 0x0500;
    CONFIG_SET     = 0x0501;
    CONFIG_RESPONSE= 0x0502;
    OTA_OFFER      = 0x0600;
    OTA_PROGRESS   = 0x0601;
    OTA_REPORT     = 0x0602;
    OTA_ROLLBACK   = 0x0603;
    TUNNEL_OPEN    = 0x0700;   // 桥接隧道（路径 D）
    TUNNEL_DATA    = 0x0701;
    TUNNEL_CLOSE   = 0x0702;
    LOG_BATCH      = 0x0800;
    ERROR          = 0xFFFF;
}
```

### 2.3 心跳语义

| 机制 | 职责 | 参数 |
| --- | --- | --- |
| 应用层心跳（HEARTBEAT） | **判定业务断线** | 5s 间隔，30s 无心跳断开 |
| TCP keepalive | 内核层回收死连接 | 默认关闭或长周期，**不用于业务判定** |

两者职责不同，不得互相替代。早期文档两套并存而未说清，已明确。

## 三、路径 C：设备端 ↔ 服务器（WebSocket/JSON）

### 3.1 消息封装

```json
{ "type": "<类型>", "id": "<uuid-v4>", "ts": "<RFC3339>", "payload": { ... } }
```

`ts` 为 **RFC3339 字符串**，不再是裸毫秒数。全系统统一。

### 3.2 消息类型

**设备 → 服务器**：

| type | 说明 |
| --- | --- |
| `hello` | `{device_id, protocol_version}` |
| `heartbeat` | `{sequence}` |
| `auth` | `{device_id, nonce, ts, sig}` 挑战应答 |
| `status` | 运动/电源/系统状态（含 `firmware_version`） |
| `data` | 传感器批量数据 |
| `ack` | `{command_id, accepted, error_code?}` |
| `result` | `{command_id, success, data?, error_code?}` |
| `config_response` | `{config_key, success, value, error_code?}` |
| `ota_progress` | `{deployment_id, progress, status}` |
| `ota_report` | `{deployment_id, status, error_code?}` |
| `log` | `{entries: [{ts, level, module, message, fields?}]}` |
| `error` | `{error_code, message, context?}` |

**服务器 → 设备**：

| type | 说明 |
| --- | --- |
| `challenge` | `{nonce, ts}` |
| `auth_ok` / `auth_fail` | `{session_id}` / `{error_code}` |
| `command` | `{command_id, command_type, params, priority, timeout_ms}` |
| `estop` | `{command_id}` 紧急停止，可插队 |
| `config` | `{config_key, value, version}` |
| `ota_offer` | `{deployment_id, kind, version, url, size, hash, signature}` |
| `ota_rollback` | `{target_version}` |
| `tunnel` | 见 §五 |

**注意**：`command` 必须含 `command_type` 与 `timeout_ms`。
早期文档只发 `params`，设备无法判断命令语义，是缺陷。

### 3.3 序列化统一

设备↔服务器**统一 JSON**。早期设备端文档用 `SerializeAsString()` 发 Protobuf
而服务器用 `ReadJSON`，两端无法互通——已修正为 JSON。

## 四、路径 B：上位机 ↔ 服务器

REST 见 `服务器端程序架构.md` §3.1。WebSocket：

| type | 方向 | 说明 |
| --- | --- | --- |
| `subscribe` / `unsubscribe` | 前端→服务器 | `{topic}`，服务器**校验设备归属** |
| `command` | 前端→服务器 | `{device_id, command_id, command_type, params, priority, timeout_ms, sig}` |
| `estop` | 前端→服务器 | `{device_id, command_id}` |
| `data` | 服务器→前端 | 订阅推送 |
| `command_state` | 服务器→前端 | `{command_id, status, error_code?, ts}` |

**认证**：JWT 不在本项目使用。WebSocket 在 HTTP Upgrade 握手时校验**会话票据**一次，
建立后不重复认证。会话失效时服务器主动关闭连接，close code：

| code | 含义 |
| --- | --- |
| 4001 | 会话已失效或已吊销 |
| 4002 | 无此设备权限 |
| 4003 | 环境不匹配 |

**命令通道语义必须与直连一致**：中转路径同样要有「等待结果 / 超时 / 失败」语义。
早期前端文档在服务器路径上硬编码返回成功（`Result.success(...)`）是安全缺陷——
降级态下操作员会看到「成功」但机器人没动。

## 五、路径 D：设备端 ↔ G30 ↔ 服务器（桥接隧道）

设备出网中断时，由上位机 G30 作为透明隧道。隧道封装在路径 A 的 TCP 连接上。

### 5.1 隧道帧

复用 §2.1 帧格式，`Type` 为 `TUNNEL_*`：

| Type | Payload |
| --- | --- |
| `TUNNEL_OPEN` | `{tunnel_id, target: "server", protocol_version}` |
| `TUNNEL_DATA` | `{tunnel_id, payload_b64}`（`payload_b64` 是 §三 JSON 消息的 base64） |
| `TUNNEL_CLOSE` | `{tunnel_id, reason}` |

- `tunnel_id`：多路复用标识，由发起方生成。
- **透传**：G30 不解析 `payload_b64` 的内容语义，只做转发。
  G30 可以看见消息但**不作为可信中介**——命令签名由设备端验证（§七）。
- **G30 自身与服务器的连接**是独立的 WebSocket（路径 B），隧道复用该连接。

### 5.2 隧道语义

- 隧道断开：G30 向设备发 `TUNNEL_CLOSE`，设备回退到离线缓存模式。
- 隧道重连：设备重新 `TUNNEL_OPEN`，交换 `protocol_version` 与 `last_applied_seq`。
- 命令冲突：桥接态下**上位机本地操作优先**，服务器下发的运动类命令被拒，
  回执 `EBUSY_LOCAL_AUTHORITY`（见 §六错误码）。

## 六、错误码

三种传输共用同一枚举。REST 直接序列化枚举名，二进制帧用编号。

```

1002 EUNAUTHORIZED      未授权

# 设备 2xxx

2004 ECOMMAND_TIMEOUT   命令超时
```

## 七、安全机制

### 7.1 传输

TLS 1.3。服务器使用标准服务端证书。**不使用 mTLS**——设备认证走挑战应答（§7.3）。

### 7.2 命令签名

**签名者：用户侧**。私钥只存在于前端 App 的 Keystore，服务器不持私钥。

```
待签内容 = canonical_json({
    device_id, command_id, command_type, params, priority, timeout_ms, ts, command_seq
})
signature = Ed25519(user_private_key, 待签内容)
```

- **canonical JSON**：键按字典序、无多余空格、`params` 内嵌套同样规范化。
  不得对语言原生的 map 直接 `fmt`/`json` 输出后签名——顺序不稳定。
- **校验点：设备端**。服务器可做一次快速校验用于早退，但**不是唯一验签点**。
- 早期方案用 HMAC + 共享密钥，三方共持等于密钥无法隔离，且只在服务器验签，
  等于服务器到设备这段没有保护——已废弃。

### 7.3 设备认证（挑战应答）

```
1. 设备建立 TLS，发 hello {device_id, protocol_version}
2. 服务器发 challenge {nonce(32B 随机), ts}
3. 设备回 auth {device_id, nonce, ts, sig = Ed25519(device_key, device_id||nonce||ts)}
4. 服务器查 device_public_keys 验签，绑定会话
```

设备私钥存于 `/etc/km3/device.key`（0600）。
**已知风险**：TL3588 无 TPM/安全元件，私钥仅靠文件权限保护，不足以抵御物理接触攻击。
接受此风险或列为「需额外硬件」的待办。

### 7.4 防重放

`command_seq` 单调递增 + 5 秒窗口 + 已见 seq 窗口缓存（如最近 256 个）。
窗口判定用**单调时钟**。重复 `command_id` 由业务层幂等去重处理。

### 7.5 固件签名

```
1. 离线：开发机 Ed25519 私钥对 firmware.bin 的 SHA256 签名
2. 产出 firmware.bin + firmware.sig + manifest.json（version/hash/size/min_version）
3. 服务器分发，设备校验 SHA256 与签名
4. 公钥表随固件下发；轮换 = 一次 OTA 更新设备内公钥表
```

### 7.6 用户端

服务端随机会话票据（非 JWT），存 Postgres，可即时吊销。
密码哈希为 Argon2id（libsodium `crypto_pwhash`）。

## 八、超时层级

全系统统一，三条路径引用同一张表（早期三份文档分别写 30s/30s/500ms，互不构成层级）：

| 层级 | 值 | 说明 |
| --- | --- | --- |
| 设备本地看门狗（运动类命令） | 500ms | 直连通道下的命令语义超时 |
| 设备本地看门狗（配置/查询类） | 5s | |
| 设备本地看门狗（服务器中转/桥接通道） | 3s | **随通道动态调整**，切换时重置 |
| 服务器命令超时 | 10s | 设备看门狗 + 网络预算 |
| 前端等待超时 | 15s | 服务器超时 + 余量 |

**通道切换时必须重置看门狗计时**，否则一次切换会立刻误触发安全模式。

### 8.1 优先级

| 级别 | 用途 |
| --- | --- |
| P1 | 紧急停止（**不走队列**） |
| P2 | 实时控制命令 |
| P3 | 配置、状态查询 |
| P4 | 数据上报 |
| P5 | 日志上传 |

紧急停止不受队列长度限制，允许插队，服务器先发后记。

## 九、会话恢复

重连（含通道切换）后：

1. 交换 `protocol_version`；不匹配则拒绝并上报 `EINCOMPATIBLE_VERSION`。
2. 交换 `last_applied_seq`；服务器重发所有未确认命令。
3. 设备按 `command_dedup` 表对 `command_id` 幂等去重，重复命令回放上次结果。
4. 通道切换时，UI 必须提示当前通道，并把「已发出未确认」的命令标记为
   **结果未知，请确认设备状态**，不得静默丢弃。

## 十、配置消息

三条路径语义一致：

| 语义 | 路径 A（Protobuf） | 路径 B/C（JSON） |
| --- | --- | --- |
| 读取 | `CONFIG_GET` | `{"type":"config_get","payload":{"config_key"}}` |
| 写入 | `CONFIG_SET` | `{"type":"config_set","payload":{"config_key","value"}}` |
| 响应 | `CONFIG_RESPONSE` | `{"type":"config_response","payload":{"config_key","success","value","error_code"}}` |

服务端额外提供 `GET /devices/:id/config/schema` 返回可配置项清单，前端据此动态渲染。

## 十一、OTA 消息

OTA 是**长事务**，不是单条命令。独立消息族：

| 语义 | 路径 A | 路径 B/C |
| --- | --- | --- |
| 下发 | `OTA_OFFER` | `{"type":"ota_offer", ...}` |
| 进度 | `OTA_PROGRESS` | `{"type":"ota_progress", ...}` |
| 结果 | `OTA_REPORT` | `{"type":"ota_report", ...}` |
| 回滚 | `OTA_ROLLBACK` | `{"type":"ota_rollback", ...}` |

进度上报间隔建议 1s 或每 5% 一次；断点续传用 HTTP Range（固件经 nginx 分发）。
详见 `OTA升级方案.md`。

## 十二、版本管理

`protocol_version` 形如 `1.0`。主版本变更不兼容，需同时升级；
次版本向后兼容，可独立升级。连接建立时协商一次，重连重协商。
