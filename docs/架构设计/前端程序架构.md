# 前端程序架构（云卓 G30 / Android 原生）

技术栈：Kotlin + Jetpack Compose。**不使用 JNI / NDK / C++**——
Protobuf 用 `protobuf-javalite` 在 Kotlin 侧生成即可，无需 native 层。

本文件描述应用架构、通道语义与界面契约。代码细节不在本文档。

## 一、架构

```
UI (Compose) → ViewModel → Repository → Data
                                          ├── DeviceLink   直连设备（TCP + Protobuf）
                                          ├── ServerLink   服务器（WS/REST + JSON）
                                          └── LocalStore   Room + DataStore
```

技术栈：

| 层 | 选型 |
| --- | --- |
| UI | Jetpack Compose + Material 3 |
| 导航 | Navigation Compose |
| 状态 | StateFlow + ViewModel |
| 注入 | Hilt |
| 网络 | OkHttp + WebSocket；`protobuf-javalite` |
| 视频 | Media3 / ExoPlayer |
| 本地 | Room + DataStore |
| 图表 | **Vico**（Compose 原生） |

**不用 MPAndroidChart**：它是 View 体系，在 Compose 里得用 `AndroidView` 互操作，
与选 Compose 的理由相矛盾。

## 二、通道管理（核心）

### 2.1 两条通道与降级

| 通道 | 链路 | 协议 |
| --- | --- | --- |
| 直连 | G30 ↔ 设备（eth1 光纤） | 自定义 TCP，14 字节头 + Protobuf |
| 中转 | G30 ↔ 服务器 ↔ 设备 | WebSocket，JSON |

优先级：直连优先，直连失败自动降级到中转。详见 `通信协议规范.md` §一。

### 2.2 通道语义必须一致（重要修正）

**两条通道的命令语义必须完全相同**：都要有「等待结果 / 超时 / 失败」。

早期版本在服务器通道上硬编码返回成功：

```
// 错误，必须删除
// TODO: 实现响应等待机制
Result.success(CommandResult(success = true))
```

这是**安全相关缺陷**：降级态下操作员会看到「成功」但机器人没动。
正确做法是两条通道共用同一套 `suspend fun sendCommand(cmd): CommandResult` 语义，
由 `CommandRouter` 按当前通道分发，超时用协议规范 §八的统一层级（前端 15s）。

### 2.3 切换时的用户可见性

1. UI 常驻显示当前通道（直连 / 中转 / 离线）。
2. 切换发生时提示用户。
3. **在途未确认的命令标记为「结果未知，请确认设备状态」**，不得静默丢弃。
4. 紧急停止在任何通道都可用，且不排队。

### 2.4 设备与相机的来源（此前缺失）

- **设备列表**：`GET /api/v1/devices` 获取当前用户可管的设备，供选择。
  `device_id` 不是预先写好的偏好值，而是从列表选择后存入 DataStore。
- **相机列表**：`GET /api/v1/devices/:id/cameras` 返回该设备可用相机与流地址
  （服务器侧对应接口见服务器文档 §3.1）。
- 本机直连时，设备端 `STATUS_REPORT` 携带自身标识与能力集，用于校验与列表一致性。

## 三、界面

| 页 | 对应 | 内容 |

| 登录 | — | 账号密码登录，保存会话票据，支持服务器地址配置 |
| 设备选择 | — | 列出可管设备，选择进入 |
| 控制 | F01 F02 | 运动控制、操作参数；命令状态与 ACK 反馈 |
| 状态 | F03 | 实时状态与传感器展示（IMU / 超声波 / 气压 / 温湿度） |
| 数据 | F04 | 三维测距、实时曲线、告警 |

| 调试 | F08 | 隐藏功能、调试入口与预览（**入口与开关见 §3.3**） |

### 3.2 配置面板的动态渲染（此前为零）

配置面板不能硬编码表单，否则每加一个设备参数都要发版。流程：

1. `GET /devices/:id/config/schema` 取回可配置项清单：
   `{key, label, type, range, editable_by, current}`。
2. 按 `type` 生成控件（数值/枚举/布尔/字符串），按 `range` 设边界。
3. 按当前用户角色决定只读或可编辑（见 §4）。
4. `PUT /devices/:id/config` 提交，等待设备 `config_response` 确认闭环。

### 3.3 隐藏功能与调试入口（F08）

| 项 | 设计 |
| --- | --- |
| 入口 | 设置页「关于」连续点击 7 次 |
| 权限 | 仅 `superadmin` / `admin` 可见；服务端同样校验，不做「前端隐藏即安全」 |
| 内容 | 原始帧调试、通道强制切换、本机日志查看、预览开关、协议版本显示 |
| 开关持久化 | DataStore 记录本地开关；服务端权限为准 |
| 审计 | 调试入口内的写操作上报服务端记审计 |

## 四、权限

角色与能力矩阵见 `服务器端程序架构.md` §4.4。前端职责：

- 按角色隐藏不可用操作（**仅体验优化**）。
- 所有受限操作仍由服务端校验；前端隐藏不是安全边界。
- `viewer` 只读；`operator` 可控制与受限配置；`admin` 可管用户与升级。

## 五、登录与安全

- 登录：`POST /api/v1/auth/login` 换取**会话票据**（非 JWT），存 DataStore。
- 会话失效（服务端返回 4001 close code 或 401）：跳转登录页。
- 登出：`POST /api/v1/auth/logout`，服务端吊销票据。
- TLS：不使用明文；`usesCleartextTraffic=false`。
- **命令签名私钥存 Android Keystore**，签名在本地完成（见协议规范 §7.2）。

## 六、视频

- 播放：Media3 ExoPlayer，RTSP 流。
- 相机列表来自设备/服务器（§2.4），不硬编码。
- 多画面网格为可选模式；实际可同时观看的路数受设备侧带宽与编码能力限制，
  **参数未定案，界面需按运行时能力集渲染**，不假定固定 6 路。

## 七、状态与数据

- 实时状态：订阅 `device.<id>.status`（中转）或直连 `STATUS_REPORT`。
- 上报率：状态 1Hz；传感器降频（IMU 10Hz 等，见协议规范）。
- UI 需对低频数据做插值或平滑，避免 1Hz 刷新造成跳变。
- 历史数据：`GET /devices/:id/sensors/:type/history`，图表用 Vico。

## 八、告警

| 环节 | 设计 |
| --- | --- |
| 判定位置 | **设备端**（RT 进程内，阈值来自配置） |
| 上报 | `/event/alarm` → 服务器 → 推送 `alarm.<device_id>` |
| 前端 | 订阅后展示横幅 + 通知；严重告警用 FCM 推送 |
| 去重 | 设备侧按告警类型 + 时间窗去重 |

早期版本定义了 `AlarmEvent` 却没有阈值规则与推送落点，已补。

## 九、状态管理

```kotlin
data class AppUiState(
    val session: SessionState,
    val devices: List<DeviceSummary>,
    val selected: DeviceId?,
    val channel: Channel,          // DIRECT | RELAY | OFFLINE
    val deviceStatus: DeviceStatus?,
    val sensors: SensorSnapshot?,
    val cameras: List<CameraInfo>,
    val configSchema: List<ConfigItem>,
    val pendingCommands: List<PendingCommand>,  // 含「结果未知」项
    val alarms: List<Alarm>
)
```

`PendingCommand` 必须能表达「已发出、结果未知」状态并在 UI 上明确区分。
