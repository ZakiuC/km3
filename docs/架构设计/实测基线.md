## 二、CPU 拓扑（重要更正）

`/sys/devices/system/cpu/cpufreq/policy*` 实测：

| policy | related_cpus | 最高频率 | 对应簇 |
| --- | --- | ---: | --- |
| policy0 | 0 1 2 3 | 1296000 kHz | **Cortex-A55** |
| policy4 | 4 5 | 1608000 kHz | **Cortex-A76** |
| policy6 | 6 7 | 1608000 kHz | **Cortex-A76** |

结论：**CPU0–3 是 A55，CPU4–7 是 A76。**

架构文档把实时控制线程绑定到 CPU0–3 并称其为 A76 —— **该绑定与命名都需更正**。
正确做法是：实时控制放在 **CPU4–7（A76）**，管理/网络/日志等非实时服务放在 **CPU0–3（A55）**。

旁证：主板技术资料的 cyclictest 结果中，满载最坏唤醒延迟 CPU4–7 为 10/15/12/10 µs，
CPU0–3 为 80/23/38/66 µs，与 A76 更适合实时任务一致。

三簇调频均为 `performance`。当前内核命令行**未见 `isolcpus=`**，即尚未做 CPU 隔离。

## 七、实时性首次实测（2026-10-13 17:05）

这是**第一次在实机上以实时权限运行** km3 自己的周期循环（此前主机运行全部降级为
`SCHED_OTHER`，因为非特权环境下 `mlockall` / `SCHED_FIFO` 返回 `EPERM`）。

### 测试条件

| 项 | 值 |
| --- | --- |
| 程序 | `km3-rt-controller`（骨架，见 `device/src/apps/rt-controller/main.cpp`） |
| 周期 | 1000 µs（1 kHz），绝对时间推进 |
| 时长 / 周期数 | 10 秒 / 10000 个周期 |
| 调度 | `SCHED_FIFO` 优先级 90 |
| 亲和性 | CPU 4–7（A76 大核簇），实际落在 **CPU7** |
| 内存 | `mlockall(MCL_CURRENT \| MCL_FUTURE)` 成功 |
| 内核 | `6.1.141-rt36-00076-g8c1479751b6e-dirty`，`/sys/kernel/realtime` = 1 |
| 调频 | 三个 policy 均为 `performance` |
| CPU 隔离 | **未配置**（`/sys/devices/system/cpu/isolated` 为空） |
| 起始负载 | loadavg 1.34 / 0.46 / 0.25 |

### 结果

| 指标 | 值 |
| --- | ---: |
| ticks | 10000 |
| overruns（被吃掉的周期） | **0** |
| 实质性迟到（> 阈值 100 µs） | **0** |
| **最大迟到量** | **1 µs** |
| 环形缓冲丢弃 | **0** |

### 这证明了什么

- 在 **RT 内核 + `SCHED_FIFO` + 内存锁定 + 大核绑定** 的组合下，本程序的周期唤醒抖动
  在 1 kHz 下为 **1 µs 量级**，且 10 秒内无一周期被吃掉。
- `rt_util` 的实时设置路径（取时钟 → 锁内存 → 预触栈 → 绑核 → 提优先级）在实机可用，
  顺序正确（先绑核后提权）。
- 时基实现（单调时钟 + 绝对推进 + 迟到阈值统计）在实机上行为正确。

### 这**没有**证明什么（不得当作端到端实时性结论）

1. **循环体是空的**：当前只做一次 `memcpy` 级别的环形缓冲写入，
   没有采样、没有控制律、没有总线收发。真实控制回路的**执行时间**完全未测。
2. **无业务负载**：未接摄像头、未接 USB-RS485 / USB-CAN 模块、无 WiFi 流量、无 SSD 写入。
   资料明确要求「实时验收必须在启用这些实际业务负载的情况下进行」。
3. **无 CPU 隔离**：`isolcpus=` 未配置，中断仍可落到大核上。
   当前的 1 µs 是"运气不错"，不构成对中断干扰的免疫证明。
4. **未测端到端控制响应**：从命令到机械动作的链路包含总线帧时间、驱动器解析时间、
   机械延迟，与线程唤醒抖动不是同一个量。
5. **单次 10 秒样本**：不是长稳测试。资料中的厂测为 12 小时。

## 八、对架构文档的直接结论

1. **CPU 绑定纠正**：实时控制 → CPU4–7（A76）；非实时服务 → CPU0–3（A55）。
   文档现有表述相反，必须修正。
2. **CPU 隔离**需在内核命令行（`isolcpus=`）与 IRQ 亲和性层面完成，属平台层，
   不是应用线程自行设置即可。文档需把这一前置条件写清。
3. **存储契约**：不得使用根分区；需为 SSD/userdata 配置 UUID 稳定挂载，
   并在 systemd 中声明依赖。文档需补此条。
4. **网络带宽**：eth0 现为百兆，若设计假设千兆需实测确认。
5. **视频**：6 路摄像头当前未接入，所有关于分辨率/帧率/路数的设计
   必须标注为**待实测**，不可作为既定能力。
6. **总线**：CAN 与 USB-RS485/USB-CAN 模块当前均未接入，
   相关总线层需先按接口契约实现，待硬件到位后联调。

### 9.3 新增观测（10-13 基线未覆盖）

**内核命令行全文**：

```
storagemedia=emmc androidboot.mode=normal androidboot.verifiedbootstate=orange
root=/dev/mmcblk0p6 rcupdate.rcu_expedited=1 rcu_nocbs=all
```

- **仍无 `isolcpus=`** —— CPU 隔离未做，与 §二 结论一致。
- **`rcu_nocbs=all` 已存在**，与实时方案的已知冲突仍未解决（见 §六）。

**CAN 状态读取只能走 netlink**（实测，极易写错）：

`/sys/class/net/can0/` 与 `can1` 的 sysfs 顶层**没有任何 CAN 专有属性** —— 无
`bus_error`、`error_warning`、`bus_off`、`berr_counter`、`restart_ms`，也无
`bittiming` 目录；两个接口的 `statistics/` 各 24 项，全是内核通用网卡计数
（本板仅 `rx_bytes`/`rx_packets`/`tx_bytes`/`tx_packets` 非零）。
CAN 专有的六个计数（`re-started`、`bus-errors`、`arbit-lost`、`error-warn`、
`error-pass`、`bus-off`）由 **rtnetlink** 的 `IFLA_INFO_XSTATS` 提供，
`ip -details -statistics` 打印的正是它们。
**因此驱动的总线健康度采集必须基于 netlink socket。**

**无电机时的回归手段**：`vcan` 不可用（`CONFIG_CAN_VCAN` 与 `CONFIG_CAN_VXCAN`
均未设置，且无对应模块目录），替代方案是 **CAN 控制器硬件回环**，已实测可用：

```sh
ip link set can0 down
ip link set can0 type can bitrate 500000 loopback on
ip link set can0 up
candump -n 1 can0 & ; cansend can0 123#DEADBEEF   # 实测收到  can0  123  [4]  DE AD BE EF
ip link set can0 down
ip link set can0 type can bitrate 500000 loopback off
ip link set can0 up
```

它把「软件错」与「接线错／设备不在线」分开，但**不验证电气层与真实从站行为**，
不能替代实机验收。

**板载能力**（决定工具如何交付）：can-utils 全套
（`candump`/`cansend`/`cangen`/`cansniffer`/`canbusload`/`canplayer`/`canfdtest`/`slcan_attach`）、
`gcc`/`g++`/`cmake`/`make`/`pkg-config`、python3 3.10.12、ncurses 运行库
（`libncursesw.so.6` 等）均在；`tput colors` 返回 256，256 色转义可用。
**但 SSH 会话下 `stty size` 返回 `0 0`** —— TUI 必须处理「尺寸不可知」，
否则首屏即崩。

**交叉编译的两条相反结论**（同一工具链，差别在 sysroot 内容）：

| 目标 | 结果 | 原因 |
| --- | --- | --- |
| SocketCAN + termios + netlink 真后端 | **可编译**（c++17 与 c++20 均成功） | `linux/can*.h`、`termios.h` 位于 `/usr/aarch64-linux-gnu/include` |

### 9.4 对架构文档的直接结论（本次新增／修订）

1. §四「两路 CAN 未启用」、§五「无 `ttyUSB*`」、§六「部署前提尚未满足」三处已过期，
   均已加指针指向本节。**历史值保留**，因为「曾经缺什么」对复现环境有意义。
2. `hal/can_device.hpp` 的 `CanBusStats` 采集**必须基于 netlink**，
   不能假设 sysfs 存在 CAN 专有计数文件。注意「`ip` 能显示」不等于「sysfs 里有」——
   `ip` 命令本身就走 netlink。
3. 总线相关的测试与工具，在无对端设备时以**控制器回环**为回归路径；
   `vcan` 在本板不可用是内核配置决定的事实，不要再假设可用。
4. **`/dev/ttyUSB0-3` 的存在不等于 RS485 模块已接入** —— 提供者待核对，
   核对前不得据它推断硬件已就位。
