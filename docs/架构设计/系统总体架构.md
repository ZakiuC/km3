# 系统总体架构

设计日期：2026-10-13（修订版）。设计目标：高效、解耦、易于长期开发、方便 agent 与人类协同。

本文件是三端协作的**拓扑与边界**权威。模块内部细节见各端文档，接口细节见 `通信协议规范.md`。

## 一、终端与职责

| 端 | 硬件 | 技术栈 | 职责 |
| --- | --- | --- | --- |
| 设备端 | TL3588（RK3588，8GB/64GB eMMC，Ubuntu 22.04 + PREEMPT_RT） | C++17，原生部署 | 被控机器人：实时控制、采集、本地缓存、OTA |
| 上位机端 | 云卓 G30 | Android 原生（Kotlin） | 操作控制台：控制、显示、配置、升级 |
| 服务器端 | 阿里云 VPS | C++17，原生部署 | 账号权限、设备管理、命令与数据、日志、OTA |
| 管理端 | 浏览器（管理员桌面） | TypeScript + Vue 3，静态托管 | 后台：总览、日志、用户、固件下发 |

技术栈为 **C++（设备/服务器）+ Kotlin（控制台）+ TypeScript（管理端）**。
选择统一 C++ 的主要收益不是性能，而是**同一份协议定义、同一份签名与验签实现、
同一份错误码**，可显著减少行为不一致。

**管理端是第四类客户端，不与设备端直连**，只经服务器 REST/WebSocket 访问，
因此不实现帧编解码、隧道与挑战应答。它**不下发运动控制命令**——
命令签名要求用户侧私钥，而浏览器无法提供等价的密钥保护（见
`管理端Web程序架构.md` §1.2）。

## 二、网络拓扑与连接策略

### 2.1 四条路径

```
路径 A（主）：上位机 ──直连──► 设备端          [光纤/GbE，低延迟]
路径 B（降级）：上位机 ──► 服务器 ──► 设备端    [直连失败时]
路径 C（主）：设备端 ──直连──► 服务器          [出站 Internet]
路径 D（降级）：设备端 ──► G30 ──► 服务器      [设备出网中断时，经上位机桥接]
```

**权威规则：任一时刻只有一条命令通道生效**（single command authority）。

- 直连可用时，上位机的控制命令走路径 A，服务器只做数据与状态同步。
- 直连不可用时，控制命令走路径 B，由服务器转发。
- 设备出网中断时，服务器经路径 D 与设备通信。
- 桥接态（D）下，**上位机的本地操作优先**；服务器下发只允许读类与配置类命令，
  运动类命令被拒绝并回执 `EBUSY_LOCAL_AUTHORITY`。

### 2.2 两个状态机

```
设备↔服务器（路径 C/D）:
  直连可用 ──断──► G30 桥接 ──恢复──► 直连可用
  两者皆不可用 ──► 离线缓存（本地 30 天，恢复后补传）

上位机↔设备（路径 A/B）:
  直连可用 ──断──► 服务器中转 ──恢复──► 直连可用
```

切换必须满足：
1. **通道状态对用户可见**。UI 显式显示当前通道，切换时提示。
2. **在途命令不得静默丢失**。切换时，未确认的命令标记为「结果未知」并要求用户确认设备状态。
3. **切换后重建会话**：交换协议版本与 `last_applied_seq`，服务器重发未确认命令，
   设备按 `command_id` 幂等去重（见协议规范 §九）。
4. **看门狗阈值随通道变化**：直连 500ms、服务器中转/G30 桥接 3s；切换时重置计时。

### 2.3 物理接口分配（待现场确认）

| 用途 | 接口 | 现状 |
| --- | --- | --- |
| 上位机直连 | eth1（原生千兆 RGMII） | 实测 DOWN，未接线 |
| 出站 Internet | eth0 | 实测 100Mb/s，**未达千兆** |
| 4G 备份 | usb0（Quectel EM05/EC25） | 在线 |

**千兆链路未实测**。业务带宽预算不得建立在 1Gbps 假设上；eth0 当前 100Mb/s。
G30 侧的图传对接方式、协商速率、以及 G30 应用作为 TCP 服务端还是客户端的角色，
**均待与 G30 实物核对后写入配置**。

## 三、核心设计原则

1. **实时路径极简**：RT 线程只做采样、控制计算、定长记录写入预分配环形缓冲；
   不做动态分配、锁等待、文件 IO、日志格式化、网络收发、序列化。
2. **边界线程转发**：非实时线程消费环形缓冲，负责序列化与网络。
3. **模块按故障隔离拆分，不按「架构完整」拆分**。设备端保留 3 个进程（见 §9.2）。
4. **配置与数据不落根分区**：根分区实测仅剩 4.2 GiB。
5. **逻辑名与物理名分离**：业务代码不出现 ttyS 编号、GPIO 全局号、mmc 分区号、DRM plane ID。
6. **不引入无用中间件**：能用数据库和进程内事件总线解决的，不引入独立消息队列与时序库。

## 四、技术栈

### 4.1 设备端

| 层 | 选型 |
| --- | --- |
| 语言 | C++17 |
| 构建 | CMake 3.20+ |
| 进程间通信 | 有界无锁环形缓冲（RT 边界）+ Unix 域套接字（控制面） |
| 序列化 | Protobuf（内部/二进制）、JSON（对服务器与前端） |
| 日志 | spdlog |
| 配置 | nlohmann/json |
| 数据库（本地缓存） | SQLite |
| 视频 | V4L2 + RK MPP |
| 加密 | libsodium（Ed25519）、OpenSSL（TLS） |

### 4.2 服务器端

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 语言 | C++17 | 与设备端共享协议、签名、JSON 规范 |
| 构建 | CMake + 系统包 | 原生部署，不用容器 |
| 网络 | Boost.Asio + Boost.Beast | HTTP + WebSocket + TLS + 定时器统一 |
| JSON | nlohmann/json | 与设备端一致 |
| 数据库 | PostgreSQL 16（本机） | 关系 + 时序（按月分区表）+ 会话，单库 |
| 连接 | libpqxx | 不用 ORM |
| 加密 | libsodium（Ed25519/签名）、OpenSSL（TLS） | |
| 日志 | spdlog | 与设备端一致 |
| 部署 | systemd + nginx（TLS 终止与固件分发） | 原生 |

**明确不引入**：Docker、Kubernetes、Redis、InfluxDB、RabbitMQ、NATS、gRPC、ORM、微服务。

会话票据用服务端随机 `session_id` 存库（并发量极小，查库成本可忽略），换来最直接的吊销语义。

### 4.3 前端

| 层 | 选型 |
| --- | --- |
| 语言 | Kotlin（**不使用 JNI/C++**，Protobuf 用 `protobuf-javalite`） |
| UI | Jetpack Compose |
| 架构 | MVVM + Repository |
| 注入 | Hilt |
| 网络 | OkHttp + WebSocket、`protobuf-javalite` |
| 视频 | Media3 / ExoPlayer |
| 本地 | Room + DataStore |
| 图表 | Vico（Compose 原生，不用 MPAndroidChart） |

### 4.4 管理端（Web）

| 层 | 选型 |
| --- | --- |
| 语言 | TypeScript（`strict`） |
| 框架 | Vue 3 + Composition API |
| 构建 | Vite（产物为静态文件，**服务器不引入 Node 运行时**） |
| 路由 / 状态 | Vue Router / Pinia |
| UI / 图表 | Element Plus / ECharts |
| 包管理 | pnpm |
| 部署 | nginx 静态托管，与 `/api/v1` 同源 |

详见 `管理端Web程序架构.md`。选择 Vue 的理由是**决策面更小**——
官方配套的路由与状态库把选型从六七个降到两三个，对"人类决策、agent 落地"
的协作模式，决策点少即漂移少。

## 五、安全

| 项 | 方案 |
| --- | --- |
| 传输加密 | TLS 1.3；服务器证书为服务端证书 |
| 设备认证 | 设备内置 Ed25519 私钥（`/etc/km3/device.key`，0600），
握手时服务器发 nonce，设备回 `Ed25519(device_id‖nonce‖ts)`，服务器查公钥表 |
| 用户认证 | 服务端随机会话票据（非 JWT），存 Postgres，可即时吊销 |
| 命令签名 | **用户侧 Ed25519 私钥签名（私钥只在前端 Keystore）**，设备用公钥验签。
服务器不是唯一验签点，不得作为可信中介 |
| 防重放 | 单调 `command_seq` + 5 秒窗口 + 已见 seq 窗口缓存；窗口基于**单调时钟** |
| 固件签名 | **离线签名**：开发机持 Ed25519 私钥，产出 `firmware.bin/.sig/manifest.json`；
服务器只分发，不持私钥。轮换 = 一次 OTA 更新设备内公钥表 |
| 最小权限 | 业务不以 root 运行。串口/CAN 用 udev 规则授予组权限；
实时调度与内存锁定用 `AmbientCapabilities=CAP_SYS_NICE CAP_IPC_LOCK` 单独授予 |

**已知风险（如实记录）**：TL3588 无 TPM/安全元件，设备私钥只能靠文件权限保护。
这不足以抵御物理接触攻击。需接受此风险，或将其列为「需额外硬件」的待办。

## 六、数据流

### 6.1 命令（含反馈闭环）

```
上位机 ──签名命令──► [服务器准入/排队] ──► 设备端 ──► ACK ──► 执行 ──► RESULT
   │                                          │
   └──────── 结果未知时要求用户确认 ◄──────────┘
```

- 命令准入、排队、结果跟踪见服务器文档；状态机与超时层级见协议规范 §八。
- **紧急停止不参与普通队列**：独立消息类型，允许插队，服务器先发后记，
  设备端有独立通道，不受队列长度限制。

### 6.2 传感器数据

```
硬件 → RT 线程 → 环形缓冲 → 边界线程 → 本地 SQLite（30 天）
                                    └→ 批量上报（zstd）→ 服务器 → 前端
```

采样率与上报率分离（IMU 100Hz→10Hz 等），**容量上限与保留策略为待定参数**，
需按实测采样率计算后填入，不得只写「30 天」。

### 6.3 视频

```
摄像头 → V4L2/ISP → 编码(RK MPP) → ┬→ 本地录制（默认关闭）
                                   └→ 推流（RTSP）→ 上位机
```

摄像头数量、分辨率、帧率、格式**均未定案**，且实测 6 路摄像头当前未接入。
参数全部走配置。带宽瓶颈在 USB（与 4G/WiFi/串口模块共享），必须实测。

## 七、硬件基线与时序约束

设备端硬件的实测基线（CPU 分簇、存储、网络、外设现状）见 `实测基线.md`，此处只列与架构强相关的：

- **CPU0–3 = Cortex-A55（小核，≤1296MHz），CPU4–7 = Cortex-A76（大核，≤1608MHz）**。
  实时控制绑 CPU4–7，非实时服务绑 CPU0–3。
- **CPU 隔离须在平台层完成**：`isolcpus=` 内核命令行 + IRQ 亲和性。当前**未配置**。
  线程 CPUAffinity 只做迁移约束，**不等于隔离中断**。
- **CAN 仅支持 CAN 2.0B**（主板 SPI + SIT2515T），**不支持 CAN FD**。
  标称 CANfd 的设备必须走 USB 转 CAN 模块。
- **根分区仅剩 4.2 GiB**；数据盘须按 UUID 稳定挂载，服务用 `RequiresMountsFor=` 依赖。
- 硬件看门狗为 **MAX6369 + J3 跳线**，当前跳线状态待确认；喂狗者须能判断业务是否前进。

## 八、实时性

| 项 | 目标 | 状态 |
| --- | --- | --- |
| 控制周期（唤醒抖动） | 1ms | **已实测**：1 kHz × 10000 周期，最大迟到 1 µs，0 overrun |
| 控制回路执行时间 | 装入 1ms 内 | **未实测**（当前循环体为空） |
| 端到端控制响应 | ≤5ms | 设计目标，未实测 |
| 紧急停止链路 | 尽可能快 | **无实测依据** |
| 真实负载下的最坏抖动 | — | **未实测**（未接视频/USB外设/WiFi/SSD写入） |

厂家 cyclictest 数据是**线程唤醒延迟**（CPU4–7 满载最坏 10/15/12/10 µs），
**不等于端到端控制响应**——后者还含总线帧时间、驱动器解析与机械动作。

**km3 自身已取得首个实测点**（2026-10-13，10 秒 / 1 kHz / `SCHED_FIFO` 90 / CPU7 /
内存锁定，未配置 `isolcpus`）：最大迟到 **1 µs**，0 overrun，0 丢弃。
但**循环体为空**，且无任何业务负载，因此这只是"时基与调度可用"的证据，
**不是**控制回路的实时性结论。完整条件与边界见 `实测基线.md §七`。

验收前仍必须在真实负载（视频 + USB 外设 + WiFi + SSD 写入）下测**最坏**响应时间，
并补测控制回路的**执行时间上界**。

## 九、模块化与部署

### 9.1 设备端进程（3 个）

| 进程 | 内容 | 特权 |
| --- | --- | --- |
| `km3-rt-controller` | 实时控制、安全监控、HAL | CAP_SYS_NICE + CAP_IPC_LOCK |
| `km3-core` | 网络、配置、日志、OTA、数据采集 | 普通用户 |
| `km3-video` | 视频采集与编码（独立，因会背压） | 普通用户 |

早期版本拆成 7 个进程属过度设计，已合并。配置与日志是 `km3-core` 内的模块，不单独起进程。

### 9.2 服务命名（唯一权威）

设备端 systemd 单元：`km3-rt-controller.service`、`km3-core.service`、`km3-video.service`、
`km3-can.service`（CAN 配置）。**其他文档引用服务名一律以此为准。**

### 9.3 部署路径

| 类别 | 位置 |
| --- | --- |
| 程序与只读资源 | `/opt/km3/`（根分区） |
| 配置 | `/etc/km3/`（根分区） |
| 日志、缓存、录像 | `/data/`（数据盘，UUID 挂载） |
| 版本化模块（增量更新用） | `/opt/km3/releases/<version>/` + `current` 符号链接 |

服务器端与管理端（均在 VPS 上，原生部署）：

| 类别 | 位置 |
| --- | --- |
| 服务器端程序 | `/opt/km3-server/releases/<version>/` + `current` 符号链接 |
| 服务器端配置 | `/etc/km3-server/config.json` |
| 管理端静态产物 | `/opt/km3-web/releases/<version>/` + `current` 符号链接 |
| TLS 与静态托管 | nginx：同一域名下 `/` 提供管理端静态文件，`/api/` 反代到本机 `km3-server` |

管理端与 `/api/v1` **必须同源**：会话票据走 HttpOnly + SameSite=Strict Cookie，
跨源会使该设计直接失效（见 `管理端Web程序架构.md` §四、§八）。
管理端部署**不引入 Node 运行时**，产物是静态文件。

### 9.4 OTA 的边界

| 对象 | 方式 |
| --- | --- |
| `km3-core`、`km3-video`、HAL 之外的用户态模块 | 增量热更新：版本目录 + 符号链接原子切换 + 服务重启 |
| `km3-rt-controller`、内核、设备树 | 整包停机更新 |
| 不含实时路径的辅助能力（视频参数、上报策略、日志过滤） | 可选 `dlopen` 插件，带 `ABI_VERSION`，不匹配即拒绝加载 |

**A/B 双系统当前不具备**：实物为普通分区布局，且资料说明 A/B 需专用镜像、
只支持 eMMC 启动、根文件系统引导失败时可能不会自动重启。第一版按
「停机 + 单分区替换 + 失败手工恢复」实现，自动回滚列为后续改造任务。
详见 `OTA升级方案.md`。
