# 开发规范

技术栈：**C++17（设备端 + 服务器端）+ Kotlin（Android 前端）**。原生部署，不用容器。

## 一、编码规范

### 1.1 通用约定

| 项 | 约定 |
| --- | --- |
| 缩进 | 4 空格（C++/Kotlin），2 空格（JSON/YAML/CMake），Tab（Makefile） |
| 行宽 | 100 |
| 编码 | UTF-8，LF 换行 |
| 格式化 | `clang-format`（配置见仓库根 `.clang-format`） |
| 静态检查 | `clang-tidy`（配置见 `.clang-tidy`） |

### 1.2 C++ 命名（设备端与服务器端统一）

| 类别 | 风格 | 示例 |
| --- | --- | --- |
| 类 / 结构体 | PascalCase | `MotionController` |
| 函数 / 方法 | PascalCase | `ClimbRope()` |
| 变量 | snake_case | `max_speed_mps` |
| 成员变量 | snake_case + 后缀下划线 | `value_` |
| 常量 | `k` + PascalCase | `kMaxRetries` |
| 枚举类型 | PascalCase | `ConnectionState` |
| 枚举值 | PascalCase | `ConnectionState::Connected` |
| 命名空间 | lower_case | `km3::control` |
| 指针/引用 | 符号靠类型 | `int* p`, `const std::string& s` |

### 1.3 C++ 关键约束

```cpp
#pragma once

#include <memory>
#include <string>

namespace km3::control {

class MotionController {
public:
    MotionController();
    ~MotionController();

    MotionController(const MotionController&) = delete;
    MotionController& operator=(const MotionController&) = delete;
    MotionController(MotionController&&) = default;

    Result ClimbRope(float speed_mps, Direction dir);

private:
    std::unique_ptr<CanBus> can_bus_;
};

}  // namespace km3::control
```

- 错误用 `Result` 返回码或 `std::expected`（C++23 可用时），**不抛异常穿过实时路径**。
- 优先智能指针；`auto` 用于类型明显处。
- 禁止裸 `new`/`delete`；禁止 `malloc` 出现在实时路径。

### 1.4 实时路径纪律（设备端，最重要）

**RT 线程内禁止**：

- 动态分配（`new`、`malloc`、容器扩容、`std::string` 拼接）
- 锁等待（`mutex`、`std::lock_guard`）
- 文件 IO、日志格式化、网络收发
- 序列化（`SerializeToString`、JSON 解析）
- 相对睡眠（`sleep_for`）——用单调时钟绝对推进

**跨实时/非实时边界**：预分配**有界无锁 SPSC 环形缓冲**，定长记录，
`std::atomic<uint32_t>` 头尾指针。RT 线程只做 `memcpy`；由 SCHED_OTHER 的边界线程出队、
序列化、转发。

**配置读取**：启动时把配置快照成 POD 结构体，RT 线程只读原子快照指针；
运行时变更由边界线程完成并原子换指针。**禁止 RT 线程读 JSON / 持锁取值**。

**时间源**：`MonotonicUs()`（`CLOCK_MONOTONIC`）用于超时、看门狗、周期推进、数据裁剪；
`WallClockUs()` 用于对外上报、日志、签名。RT 路径只允许前者。

### 1.5 Kotlin 命名

| 类别 | 风格 |
| --- | --- |
| 类 / 接口 | PascalCase |
| 函数 / 变量 | camelCase |
| 常量 | SCREAMING_SNAKE_CASE |
| 包名 | 小写点分 |

优先 `val`；协程用 `viewModelScope`；空安全用 `?.` / `?:`。

## 二、Git 工作流

### 2.1 分支

```
main          生产，仅接受 develop / hotfix 合并
develop       开发主线
feature/xxx   从 develop 出，回 develop
hotfix/xxx    从 main 出，回 main 与 develop
```

### 2.2 提交消息

```
<type>(<scope>): <subject>

<body>

<footer>
```

`type`：`feat` / `fix` / `docs` / `style` / `refactor` / `perf` / `test` / `chore`。

示例：

```
fix(device): correct RT thread CPU affinity to big cores

CPU0-3 are A55 and CPU4-7 are A76 on RK3588. The 1kHz control
loop was bound to the little cores.

Refs: docs/架构设计/实测基线.md
```

### 2.3 提交前检查

1. `clang-format` 已应用。
2. `clang-tidy` 无新增告警。
3. 单元测试通过。
4. 文档与代码一致（接口变更必须同步文档）。

## 三、测试

### 3.1 分层

| 层 | 工具 | 覆盖目标 |
| --- | --- | --- |
| 单元（C++） | 仓库自带 `device/tests/test_harness.hpp`（零依赖） | 核心逻辑 > 70% |
| 单元（Kotlin） | JUnit + MockK | ViewModel / Repository |
| 集成 | 同一 harness + 模拟设备 | 模块间契约 |
| E2E | Compose UI Test + 实机 | 关键路径 |
| 单元（管理端 Web） | Vitest | 权限判定、请求层、store |
| E2E（管理端 Web） | Playwright | 登录、环境切换、日志查询 |

### 3.2 必须有的模拟件

- `MockCanBus` / `MockRs485Bus`：注入帧、断言发送。
- 模拟设备端：用于前端与服务器联调，不必连真机。

### 3.3 消毒器（CI 必跑）

```sh
# 每个 C++ 目标在 CI 中至少跑一次
# 开关是 -DKM3_SANITIZER，不要在 CMAKE_CXX_FLAGS 里手写 -fsanitize：
# 手写只作用于编译、不作用于链接，且 address 与 thread 同时开启会被编译器拒绝。
cmake -S device -B build-asan -DKM3_SANITIZER=address   # ASan + UBSan
cmake -S device -B build-tsan -DKM3_SANITIZER=thread    # TSan（与 address 互斥）
cmake --build build-asan -j"$(nproc)" && ctest --test-dir build-asan --output-on-failure
```

**TSan 对服务器端（Asio 回调生命周期、会话表并发）是必需的**——
这类问题是最可能的线上奇怪崩溃来源。

### 3.4 实时性回归

实时相关改动必须附带实测数据（cyclictest 或最坏响应时间），不能只跑功能测试。

on: [push, pull_request]

  device:
    runs-on: ubuntu-22.04
    steps:

      - uses: actions/checkout@v4

### 3.5 管理端 Web

```sh
cd admin-web
pnpm install --frozen-lockfile
pnpm run typecheck     # vue-tsc --noEmit
pnpm run test:unit     # Vitest
pnpm run build         # 静态产物 dist/
```

**要求 pnpm ≥ 10**（本机在 11.7.0 上验证，CI 同版本）。这是硬下限而非偏好：
依赖的构建脚本白名单以 `allowBuilds`（映射、布尔值）写在 `pnpm-workspace.yaml` 中，
pnpm 9 不识别该键，安装会以 `ERR_PNPM_IGNORED_BUILDS` **非零退出**，CI 第一步即失败。

`pnpm run build` 在 CI 中必须执行：类型检查通过不代表构建通过，
`.vue` 单文件组件的模板编译有自己的错误面。详见 `管理端Web程序架构.md` §九。

## 五、部署

### 5.1 设备端

```sh
# 构建（交叉编译）
cmake -S device -B build-arm64 \
      -DCMAKE_TOOLCHAIN_FILE=device/cmake/aarch64-linux-gnu.cmake \
      -DCMAKE_BUILD_TYPE=Release
cmake --build build-arm64 -j"$(nproc)"

# 部署到版本目录并原子切换
tools/deploy_device.sh --host 192.168.0.188 --version "$(git describe --tags)"
```

部署脚本要点：上传到 `releases/<version>/`，切换 `current` 符号链接，
重启服务，健康检查，失败切回上一版本。**不停机更新只适用于 `km3-core` / `km3-video`**；
`km3-rt-controller` 变更须停机。

### 5.2 服务器端

```sh
cmake -S server -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build -j
tools/deploy_server.sh --version "$(git describe --tags)"
```

rsync 到 `releases/<version>/` → 重启 systemd 单元 → `/readyz` 健康检查 →
失败切回上一版本。**不使用 Docker。**

### 5.3 管理端 Web

```sh
cd admin-web && pnpm install --frozen-lockfile && pnpm run build
tools/deploy_web.sh --version "$(git describe --tags)"
```

上传 `dist/` 到 `/opt/km3-web/releases/<version>/` → 切换 `current` 符号链接 →
校验 `index.html` 可访问。**静态站点的回滚就是切回上一个目录，无需停机。**

两点注意：

- `index.html` 必须**不缓存**（否则发版后客户端拿到旧入口、引用已删除的带 hash 资源）；
  带 hash 的资源则可长缓存。
- 管理端与 `/api/v1` 必须同源（nginx 同域），否则 Cookie 会话与会话恢复失效。

### 5.4 数据库迁移

编号 SQL 文件放 `server/migrations/`，用 `psql -f` 顺序执行。
**不引入迁移框架**——单人项目里框架的抽象层是负资产。

## 六、文档

- `docs/架构设计/` 是设计权威；接口变更必须同步文档，否则视为未完成。
- 架构文档只保留**边界、接口签名、数据格式、状态机、部署拓扑、验收标准**。
  超过 15 行的代码块移入代码仓库，文档用链接引用。
  （这条规则的起因：早期 7 份文档 7700 余行，含大量实现片段，会与真实代码形成两份真相。）
- 每个模块目录要有 `README.md`：职责、接口、依赖、测试方式。

## 七、协同模式

### 7.1 分工

| 角色 | 职责 |
| --- | --- |
| 人类 | 架构决策、接口契约、需求确认、硬件调试、现场验证、安全关键代码审查 |
| Agent | 实现、单元测试、文档、重构、样板代码、静态检查修复 |

### 7.2 接口契约优先

**先固定头文件与协议，再让 agent 填实现**。这样既约束了实现，也降低
C++ 模板错误信息对生成质量的影响。

### 7.3 安全关键代码

以下改动必须人工审查并实机验证，不得仅凭测试通过合并：

- RT 线程内的任何改动
- 安全监控与紧急停止
- 看门狗喂狗逻辑
- 签名与验签
- OTA 的下载、校验、写入
