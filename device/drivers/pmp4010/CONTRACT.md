# pmp4010 驱动契约

本文件是 `pmp4010` 驱动与**上游调用方**（控制律、安全监控、诊断工具）之间的约定。
接口签名以 `driver/pmp4010_driver.hpp` 为准；本文件只写它约束不了的东西：
时序、线程、以及**当前阻塞在哪里**。

> **反馈能力不在这里声明。**「PMP4010 有没有回读」只在
> `docs/硬件手册/PMP4010/README.md` 的「反馈能力」小节声明**一次**
> （取值 `none` / `readback` / `cyclic`）。写两处就是两份真相，
> 而换硬件时必然漏改一处。本文件可以**引用**那一节，但不能复制它的结论。

> 「完成判据」的最后一条：这一节不许留「待确认」。

## 一、阻塞项

### 1.1 PDO 默认映射未知 —— 直接决定 1 ms 周期与端到端目标是否成立

CANopen 的周期指令有两条路，成本差一个量级：

| 路径 | 报文形态 | 一次往返 | 能否 1 ms |
| --- | --- | --- | --- |
| PDO | 单帧，无协议开销，由 SYNC 或事件触发 | 帧时间量级 | 可以 |
| SDO | 请求 / 应答**事务**，带 index/sub/命令字，且需等应答 | 两个帧时间 + 从站处理 + 软件等待 | 不可以 |

`docs/架构设计/开发规范.md §1.4` 禁止实时线程做「网络收发」、「锁等待」、
「相对睡眠」——而 SDO 的语义**就是**「发出去、等应答、再继续」，是一次
跨总线的阻塞事务。因此：

- SDO **只能待在边界线程**（`BoundaryThread`，SCHED_OTHER）。它可以出现在启动
  配置、参数写入、故障后重配、诊断工具里，**不得出现在 1 ms 周期路径上**。
- 周期路径只能走 PDO。而 PDO 能不能用，取决于**从站的默认 PDO 映射**：
  - 若默认映射里已经包含「控制字 + 目标位置 / 目标速度」且可映射，
    周期路径成立，本驱动只做映射校验与 SYNC 节拍。
  - 若默认映射为空、或未包含所需对象、或不允许改写（映射不可变），
    **周期路径必须重新设计**：要么退化为「1 ms 周期 + SDO」并接受端到端目标
    不成立（那就不该叫 1 ms），要么改由从站自身的插补 / 速度模式吸收。
    二者都是**架构决策**，不是本驱动的实现细节，须由人决定。
  - 若从站提供 EDS / DCF（手册条目 C8），映射可从文件读出，本项直接消解。

**在 `od.json` 的 PDO 条目拿到 `status=verified` 之前，本驱动不实现周期路径。**
现有骨架里 `MoveTo` / `SetVelocity` 是**一次性指令**语义，不是周期指令语义；
把它们接进 1 ms 循环是错的。

## 二、RT 可达性

**结论：本驱动没有任何函数可进实时线程。** 这是**未核对**状态下的正确结论，
不是待办。下表逐函数给出依据（规格要求「逐函数填好」，见
`docs/架构设计/硬件驱动开发路径.md` 第 3 步的完成判据）。

| 函数 | 可进 RT | 依据 |
| --- | --- | --- |
| `Pmp4010Driver::Open` / `Close` | **否** | 构造与析构 `std::string`（逻辑名、配置）；且属初始化路径 |
| `Pmp4010Driver::ProbeNode` | **否** | 经 `ICanDevice` 的收发，其实现行为未约束（可能重连、可能加锁等待） |
| `Pmp4010Driver::SendNmt` | **否** | 同上；且它影响 4 台从站的状态，必须由人确认（见第三节） |
| `Enable` / `Disable` / `MoveTo` / `SetVelocity` / `Stop` / `Home` | **否** | 同上。当前更直接的原因：`GuardTransmit` 返回错误，而"能跑起来"的那天它们仍是 SDO/PDO 事务 |
| `SdoRead` / `SdoWrite` | **否** | SDO 是请求-应答事务，语义上就是"发出去、等应答"，见第一节 1.1 |
| `GuardTransmit` | **否** | 写计数器（`DriverStats` 的 `uint64_t`）。虽无分配，但它是上面那些方法的入口，脱离调用点单独放行没有意义 |
| `Stats` / `Config` / `LogicalBus` | 是（但无用） | 只读，无分配。**刻意不声明为可入 RT**：本驱动的调用点整体在边界线程上，放行一个取值函数只会诱使别人把整条路径搬进 RT |
| `UnverifiedOdCount` / `OdEntryCount` | 是 | `constexpr`，编译期常量。**这是本驱动唯一真正可入 RT 的东西**，因为它在编译期就消失了 |

### 2.1 逐条可核查的说明

1. `Pmp4010Driver` 的所有公开方法都会调用 `ICanDevice::Send` / `Receive`，
   而 `ICanDevice` 的契约（`device/include/km3/hal/device.hpp`）明确
   「本层不做内部加锁」，并注明设备访问模式是「实时线程独占、**或边界线程独占**」。
   本驱动取的是后者：**由边界线程独占 `can-2` 的 CANopen 会话**。
2. 因此 `pmp4010_driver.cpp` 内允许出现构造 `std::string`、`std::vector`、
   打日志、等待应答、按逻辑名查配置。这些都违反 §1.4，所以**它必须在边界线程**。
3. 周期路径的形态是：RT 线程写无锁环形缓冲 → 边界线程出队 → 本驱动发帧。
   RT 线程**不持有** `ICanDevice*`，也不持有 `Pmp4010Driver*`。
4. 本驱动**不提供**任何「在 RT 线程里调用也安全」的方法，也不打算提供。
   若将来有人要把它搬进 RT 路径，那是一次架构变更：
   需先证明 PDO 映射可用（§1.1）、预分配完毕、无任何等待与分配，
   并走 `docs/架构设计/开发规范.md §7.3` 的人工审查 + 实机验证。

## 三、发帧纪律

1. `kOdVerified == false` 时，**零字节发出**。这不是「防御性编程」，是当前唯一正确的行为：
   索引未知就发帧 = 拿真实电机盲试。`tests/test_pmp4010.cpp` 把这条钉死。
2. 所有写操作前校验值域，**在发帧之前**拒绝越界值，不把兜底交给驱动器。
3. `Stop` 是唯一在未知状态下也应尽量送达的语义——但在 `kOdVerified == false` 时
   同样不发帧：连控制字索引都不确定，"停机"报文本身就可能被解读成别的东西。
   真实的停机手段是停 `km3-can.service`（总线断开后驱动器按自身故障处理），
   那属于部署与安全设计，不由本驱动实现。

## 四、与配置文件的关系

- 逻辑名 `can-2` → 物理接口的映射**只**在 `device/config/device.json` 的
  `bus.can` 数组里。本目录（含 `tools/pmp4010.py`）不得写死任何内核接口名。
- 位速率同理：`device.json` 里声明，运行时由 `/etc/km3/can.env` 的 `CAN_BITRATE=`
  交给 `km3-can.service`。接口的 up/down 与位速率**归 km3-can.service 所有**，
  本驱动与 TUI 都不接管（TUI 侧原因：km3 用户 CapEff=0，`ip link set` 报
  Operation not permitted，`systemctl restart` 报 Interactive authentication required）。
